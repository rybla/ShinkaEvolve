# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

- **Simultaneous Type-Term Co-generation**: The most successful programs (Generation 0, Score: 10.30; Generation 14, Score: 10.28) avoid the complexity of a standalone type-checker by generating the type and its corresponding term in the same recursive step. For example, the current best program returns `(("Fun", ("Int",), ty), ("Lam", "x", ("Int",), tm))`, ensuring the lambda's return type matches the body's type by construction.
- **Depth-Limited Base Case Bias**: To achieve a `good_ratio` of 1.00, successful generators (Generations 8, 11, and 14) use a `depth` parameter to force the selection of primitive literals (`Bool`, `Int`, `String`) once a threshold is reached. This prevents infinite recursion and ensures the resulting tuples match the `Ty` and `Tm` aliases.
- **Identity-Wrapping for Structural Validity**: The current best program (Generation 0) and Generation 14 utilize a pattern where recursive calls are wrapped in a `Lam` constructor. This allows the generator to increase term depth while maintaining a valid type signature, even if the bound variable is not actually used in the body.
- **Hardcoded Literal Leaf Nodes**: Using fixed, valid constants like `("Int", 27)` or `("String", "hello world")` is a proven strategy across all high-scoring programs (Generations 8, 10, 11, 14) to guarantee that the base cases of the recursion always satisfy the type aliases.

## Ineffective Approaches

- **Undefined Function Placeholders**: Generation 12 and several previous attempts (Generations 3, 6, 7) failed with a score of 0.0 because they defined the data structures but left the `generate_sample` logic as a placeholder or referenced external functions that were not in scope.
- **Static Variable Naming without Scope Tracking**: All current "correct" programs (Generations 8, 10, 11, 14) use a fixed variable name like `"x"`. While this ensures the program runs, it results in a `used_vars_proportions_average` of 0.00 because the generators do not track available variables to insert `Var` terms into the tree.
- **Omission of the `App` Constructor**: Every evaluated program to date has failed to implement the `App` (Application) constructor. This omission is the primary reason for the low `unique_subterms_proportions_average` (0.15) and the zero score for `applied_lambdas_proportions_average`.
- **Isolated Expression Blocks**: Generation 12 failed partly due to containing isolated expression blocks that did not contribute to the logic, highlighting that the evaluation environment requires a fully self-contained and functional `generate_sample` function.

## Implementation Insights

- **Minimalist Correctness vs. Functional Complexity**: The current best program (Generation 0, Score 10.30) succeeds by being "minimally correct." It prioritizes a 1.00 `good_ratio` by using a very narrow set of constructors (`LitTm` and `LamTm`), which results in a low `tm_sizes_average` (1.38) but avoids the validation errors that plague more complex attempts.
- **Type Alias Adherence**: The difference between a 10.30 score and a 0.0 score is strict adherence to the tuple-based deep embedding. Successful programs like Generation 11 exactly match the `(Constructor, *Args)` format, whereas failing programs often struggle with the nested nature of the `FunTy` and `LamTm` structures.
- **Recursive Depth Control**: The current best program uses `i = rng.randrange(0, 4 if depth > 0 else 3)` to dynamically adjust the probability of recursion. This ensures that as `depth` decreases, the likelihood of hitting a base case (Literal) increases, which is critical for generating finite, valid terms.

## Performance Analysis

- **The "Correctness Ceiling"**: There is a performance plateau around a score of 10.30. Programs like Generation 11 (10.28) and Generation 14 (10.28) are nearly identical to the best program. This suggests that simply changing literal values or minor recursion logic cannot improve the score without implementing `Var` usage or `App` terms.
- **Complexity-Correctness Trade-off**: Generation 10 achieved a slightly lower `good_ratio` (0.82) and a lower score (8.73) because it attempted more varied patterns (like returning a bound variable) without a robust environment/context tracker, leading to occasional invalid terms.
- **Metric Stagnation in Subterm Uniqueness**: All successful programs show a `unique_subterms_proportions_average` of approximately 0.15. This indicates that the current recursive strategy produces highly repetitive trees (e.g., nested identities), and significant score improvements will require a strategy that generates more diverse sub-expressions.
- **Impact of Variable Neglect**: The `used_vars_proportions_average` remains 0.00 across all successful programs. This confirms that while the programs are "correct" according to the type system, they are not yet utilizing the full power of the lambda calculus (variable binding and substitution).

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Implement a Context-Aware Variable Store**: To break the 0.00 `used_vars_proportions_average`, modify `generate_sample` to accept a `ctx: list[tuple[str, Ty]]` argument. When the generator reaches a base case (depth 0), add a weighted chance to select a variable from the context and return a `VarTm` with its corresponding type, rather than always defaulting to a `LitTm`.

2. **Introduce the Application (`App`) Constructor via Type-First Generation**: To improve `applied_lambdas_proportions_average`, implement a branch that first generates a random function type `('Fun', src, tgt)`. Then, recursively call the generator to produce a function term of that type and an argument term of type `src`, combining them into an `AppTm`.

3. **Dynamic Type Generation for Abstractions**: Instead of hardcoding `("Int",)` as the domain for all `LamTm` constructors, create a helper function `generate_type(rng, depth)` that randomly produces `Bool`, `Int`, `String`, or `Fun` types. This will increase `ty_sizes_average` and ensure that the generated function spaces are more diverse than the current nested identity patterns.

4. **Unique Variable Name Generation with Depth Tracking**: Replace the static variable name `"x"` with a unique identifier system, such as `f"v{len(ctx)}"`, to avoid shadowing and allow for complex nested terms. This ensures that when a `VarTm` is selected from the context, it refers to a specific, valid binding site, which is essential for maintaining a high `good_ratio` while increasing term complexity.

5. **Weighted Selection for Structural Diversity**: Replace the `rng.randrange` logic with `rng.choices` using depth-dependent weights. By decreasing the probability of `Lam` and `App` constructors as `depth` approaches zero, you can safely increase the initial depth limit to generate larger `tm_sizes_average` without risking infinite recursion or validation failures.
