The key insight is that we need to generate WELL-TYPED terms that:
1. Use variables (Var) - but we need to track bound variables
2. Apply lambdas (App) - but we need type-compatible functions and arguments
3. Have unique subterms - vary the literals and structure

A type-safe approach would be:
1. When generating a lambda, the body should sometimes reference the bound variable


2. When generating an application, the function must have a Fun type and the argument must match the domain type
3. Use different literals to increase uniqueness

I need a type-driven generation strategy that maintains type safety while introducing variable usage and application. The approach should generate a target type first, then recursively build a term matching that type, tracking bound variables to ensure references are valid.

For base types like Bool, Int, or String, I can return a literal value. When a variable is in scope, I can reference it with Var. For function types, I recursively generate the body while adding the parameter to the bound variables, then wrap it in a Lam. For application, I need to generate a function term and an argument term where the argument's type matches the function's domain.

The key insight is that App requires the function to have a Fun type with domain A and range B, while the argument must have type A. I can generate the function type first, then recursively build both the function and argument to match that signature.

For the function itself, I recursively generate a term of type Fun(A, B). For the argument, I recursively generate a term of type A. Then I combine them with App. This ensures type compatibility without needing complex unification.

The main challenge is that App nodes don't directly expose their component types—I need to reconstruct them from the generated terms. When I generate a function term of type Fun(A, B) and an argument term of type A, the resulting App has type B, but I lose access to A and B in the return statement. I can solve this by generating the function and argument separately, then combining them with App while preserving the type information from the original generation step.
