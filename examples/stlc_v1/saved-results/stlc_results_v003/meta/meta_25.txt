# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

*   **Aggressive Asymmetric Budget Splitting (85/15 Ratio)**: Increasing the budget split from 75/25 (Gen 19) to 85/15 (Gen 22, 25) has been the primary driver for increasing `tm_sizes_average` from ~22 to over 35. By allocating 85% of the budget to the function side of an `AppTm`, generators create extremely deep left-heavy spines, which significantly boosts structural complexity without sacrificing validity.
*   **Context-Driven Argument Type Selection**: The current best program (**Generation 22**, score 13.02) and **Generation 25** (score 12.95) utilize a strategy where `arg_ty` for an application is selected from types already present in the context (`all_tys = [t for _, t in ctx]`). This ensures that the argument branch has a high probability of finding a usable variable, directly leading to the record-high `used_vars_proportions_average` of 0.61-0.65.
*   **High-Probability Lambda Forcing (85%+)**: Forcing `LamTm` whenever the `target_ty` is a `FunTy` remains the most effective way to maximize the `applied_lambdas_proportions_average`. **Generation 23** (score 12.91) and **Generation 22** both used an 85% threshold, resulting in applied lambda proportions of 0.79-0.80, a significant improvement over earlier versions that used 80% or lower.
*   **Shadowing-Biased Variable Selection**: Consistently across all top-performing programs (Gens 20-25), selecting the most recently added variable (`matches[-1]`) rather than a random match has maintained high variable utilization. This "shadowing" preference ensures that variables from the most local scopes are prioritized, which is essential for deep, nested terms.

## Ineffective Approaches

*   **Conservative Budget Depletion**: **Generation 21** (score 12.54) used a "spine-first" approach but had a lower average term size (16.67) compared to its peers. The feedback suggests its budget-depletion logic was too conservative relative to the 90-node limit, failing to utilize the full "fuel" available for term growth.
*   **Low Initial Term Budgets**: Programs that used budgets under 120 (like earlier generations) struggled to break the 30.0 `tm_sizes_average` threshold. **Generation 23** and **Generation 22** successfully pushed sizes to 35.13 by increasing the initial budget to 150-160, demonstrating that validity can be maintained even with much larger terms if the "Hard Floor" logic is robust.
*   **Unfiltered Context Selection**: Earlier iterations that did not filter the context for specific type matches before attempting variable selection resulted in lower validity. The current successful programs all use `matches = [name for name, ty in ctx if ty == target_ty]` before deciding whether to generate a variable or a literal.

## Implementation Insights

*   **Type-Inhabitant Caching**: The current best program (**Generation 22**) implements a "caching" logic where it picks an `arg_ty` from the context 70% of the time. This creates a self-reinforcing loop: the generator creates applications for types it knows it can satisfy with existing variables, which is the key differentiator for its 13.02 score.
*   **The "Hard Floor" Variable Preference**: The most effective programs (Gens 20, 22, 25) use a 95% preference for variables over literals in the base case (`budget <= 2`). This ensures that even as the budget runs out, the generator aggressively attempts to use the context, keeping `used_vars_proportions_average` high.
*   **Dynamic Variable Naming via Context Length**: Using `f"v{len(ctx)}"` (Gens 20-25) ensures that every abstraction introduces a unique identifier. This implementation detail is responsible for the near-perfect `unique_subterms_proportions_average` (0.98), as it prevents structural collisions in the AST.
*   **Small Type Budget vs. Large Term Budget**: Successful programs maintain a small budget for `gen_type` (6-12) while using a massive budget for `gen_term` (150-160). This ensures the target type is simple enough to be inhabited while allowing the term to grow complex.

## Performance Analysis

*   **The 13.0 Score Threshold**: **Generation 22** is the first to break the 13.0 combined score barrier. This was achieved by balancing a high `tm_sizes_average` (35.13) with a high `used_vars_proportions_average` (0.61).
*   **Correlation between Spine Depth and Variable Reuse**: There is a clear correlation between the 85/15 split and variable reuse. As the spine gets deeper (Gen 22, 23, 25), the context grows larger, providing more opportunities for the "Context-Aware" selection logic to find and reuse variables.
*   **Stability of Validity**: All programs from Generation 20 to 25 maintained a 1.00 `good_ratio`. This indicates that the "Lambda Forcing" and "Context Filtering" strategies are extremely robust, allowing for aggressive experimentation with budget splits and size increases without risking type errors.
*   **Diminishing Returns on Size**: While **Generation 23** had a high score (12.91), its variable reuse (0.65) was higher than **Generation 22** (0.61), yet **Generation 22** scored higher overall (13.02) due to a better balance of term size and unique subterms. This suggests that maximizing size and variable reuse simultaneously is the current bottleneck.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Implement "Beta-Redex" Injection in Applications**: To push the `applied_lambdas_proportions_average` beyond the current 0.79 plateau, explicitly force the function side of an `AppTm` to be a `LamTm` with a 25% probability. This creates immediate `((\v. body) arg)` structures, which not only increases the lambda metric but also creates more local scopes for the "Context-Aware" logic to exploit, potentially breaking the 13.02 score barrier.

2. **Dynamic Tapered Budget Splitting**: While the 85/15 split is highly effective for size, it can lead to "starved" argument branches. Implement a dynamic split that starts at 90/10 for the first 5 levels of recursion to establish a massive spine, then shifts to 70/30 to allow the argument subtrees to grow more complex; this "tapering" should increase `tm_sizes_average` while providing more nodes for variable reuse.

3. **Frequency-Weighted Type Selection**: Refine the "Type-Inhabitant Caching" by using a `collections.Counter` to track type frequencies in the context. Instead of a uniform `rng.choice(all_tys)`, weight the selection of `arg_ty` toward types that appear most frequently; this increases the mathematical probability that the argument branch can satisfy its type requirement using a variable, pushing `used_vars_proportions_average` toward 0.70.

4. **Context-Length Dependent Lambda Forcing**: Currently, lambda forcing is a fixed 85%. Scale this probability based on context size (e.g., `0.95` if `len(ctx) < 5`, decreasing to `0.70` as the context grows) to ensure that the generator aggressively builds context early in the term's generation, providing a richer pool of variables for the deep spine to reference later.

5. **Unique Literal Generation for Leaf Nodes**: To maintain the 0.98 `unique_subterms_proportions_average` as terms grow even larger, replace static literals like `"s1"` or `500` with dynamic values such as `f"str_{len(ctx)}_{budget}"` or `rng.randint(0, 10**6)`. This ensures that even when the "Hard Floor" is hit frequently in a large term, every leaf remains structurally distinct, preventing a drop in the uniqueness metric.
