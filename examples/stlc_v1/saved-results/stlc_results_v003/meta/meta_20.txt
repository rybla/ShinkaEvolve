# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

*   **Asymmetric Budget Splitting (75/25 Ratio) for Deep Spines**: The current best program (**Generation 19**, score 12.75) and **Generation 18** (score 12.71) utilize a 75/25 or 80/20 budget split in `AppTm` nodes. By allocating 75% of the budget to the function side of an application, these generators create deep, left-heavy "spines" that maximize term size and complexity. This is a refinement of the 70/30 split used in earlier successful versions like **Generation 7**.
*   **Context-Aware Argument Type Selection**: A major driver for the high `used_vars_proportions_average` (0.53 in **Generation 19**) is the strategy of picking `arg_ty` from the existing context during application generation. **Generation 18** and **Generation 19** both implement a 60-75% probability of selecting a type already present in the context, ensuring that the subsequent `gen_term` call for the argument can actually find and use a variable.
*   **Shadowing Preference in Variable Selection**: Favoring the most recently added variables (the end of the context list) has proven highly effective. **Generation 15** (score 12.43) and **Generation 19** (score 12.75) both use `matches[-1]` to select variables. This "shadowing" preference increases the likelihood of using local variables created by recent `LamTm` nodes, boosting the `applied_lambdas_proportions_average` to 0.75.
*   **Forced Lambda Generation for Function Types**: Consistently across the top-performing programs (**Generations 15-19**), if the `target_ty` is a `FunTy`, the generator forces a `LamTm` with high probability (80%). This ensures that the structural requirements of the type are met and maximizes the density of abstractions.

## Ineffective Approaches

*   **Unconstrained Argument Type Generation**: As seen in the feedback for **Generation 17**, even with a high budget (120), the average term size (27.12) often falls short of the target if the argument types generated for applications are too complex. **Generation 19** corrected this by using `gen_type(1)` for "invented" types, preventing the recursion from hitting base-case triggers too early.
*   **Symmetric Budgeting**: Earlier iterations and the feedback from **Generation 5** confirm that 50/50 budget splits produce "bushy" but shallow trees. This limits `tm_sizes_average` and prevents the formation of the deep application spines necessary to break the 12.70 score threshold.
*   **Random Variable Selection**: Programs that select variables randomly from the context rather than prioritizing recent ones (shadowing) or matching types specifically (as seen in the failure of **Generation 1**) result in lower variable utilization and higher rates of invalid terms.

## Implementation Insights

*   **The "Hard Floor" Logic**: The current best program (**Generation 19**) uses a strict `budget <= 2` check to trigger terminal cases. By combining this with a 95% preference for variable reuse over literals, it maintains a 1.00 `good_ratio` while maximizing the `used_vars_proportions_average`.
*   **Discrepancy between Type and Term Budgets**: Effective programs (**Generation 19**, **Generation 7**) use a small budget for `gen_type` (8-10) and a large budget for `gen_term` (100-120). This ensures the "goal" (the type) is simple enough to be inhabited, while the "solution" (the term) has enough "fuel" to become complex and unique.
*   **Dynamic Variable Naming**: Using `f"v{len(ctx)}"` (seen in **Generations 18 and 19**) ensures unique variable names that scale with recursion depth. This contributes to the high `unique_subterms_proportions_average` (0.96), as it prevents structural repetition caused by name collisions.

## Performance Analysis

*   **The Ceiling of Variable Usage**: **Generation 19** achieved the highest score (12.75) primarily by pushing `used_vars_proportions_average` to 0.53. This is a significant improvement over **Generation 7** (0.30), demonstrating that context-aware type selection for applications is the most effective way to increase variable reuse.
*   **Size vs. Validity Tradeoff**: While **Generation 17** targeted a budget of 120, it only achieved a size of 27.12. **Generation 19** achieved a size of 22.60 with the same budget but a higher overall score due to better variable integration (0.53 vs 0.49). This suggests that after a certain point, increasing term size yields diminishing returns compared to increasing variable usage and lambda density.
*   **Consistency of Unique Subterms**: Across all top programs (**Generations 15-19**), the `unique_subterms_proportions_average` remains extremely high (0.96-0.97). This indicates that asymmetric budgeting and dynamic naming are highly effective at preventing the generator from falling into repetitive structural patterns, regardless of the specific split ratio (70/30 vs 80/20).

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Implement "Context-Aware" Application Probability**: Currently, the generator uses a fixed 75/25 budget split for applications. To further increase `used_vars_proportions_average`, modify the `AppTm` logic to only trigger an application if the context contains at least one variable that could serve as a function or an argument, otherwise defaulting to a `LamTm` or `LitTm`. This ensures that the "deep spines" created by the asymmetric split are populated with meaningful variable references rather than just more literals.

2. **Introduce "Type-Inhabitant" Caching for Arguments**: In the `AppTm` case, when selecting an `arg_ty` from the context (the 60% branch), prioritize types that have appeared multiple times in the `ctx`. By selecting a "popular" type for the argument, you increase the likelihood that the `gen_term` call for the argument side can select from multiple variable options, further pushing the `used_vars_proportions_average` beyond the current 0.53 ceiling.

3. **Dynamic Asymmetric Splitting based on Depth**: While the 75/25 split is successful, it can be refined by making the ratio dynamic based on the current recursion depth. At low depths (near the root), use a 90/10 split to force an extremely deep spine; as depth increases, shift toward a 60/40 split to allow the "leaves" of the spine to develop more complexity. This "tapered" approach could break the current `tm_sizes_average` plateau of 22.60 without sacrificing validity.

4. **Implement "Beta-Redex" Injection**: To boost `applied_lambdas_proportions_average` (currently 0.75), explicitly force the function side of an `AppTm` to be a `LamTm` with a 20-30% probability. When this occurs, the generator should create a `LamTm` whose body is then generated with the remaining function budget, creating immediate `((\v. body) arg)` structures that increase both structural density and the complexity of the term's data flow.

5. **Refine the "Hard Floor" with Type-Specific Literals**: The current "Hard Floor" logic (budget <= 2) uses a small set of fixed strings like `["x", "y", "z"]`. To maintain the high `unique_subterms_proportions_average` (0.96) as terms grow, replace these with a generator that produces unique literals based on the current budget or context length (e.g., `f"s_{len(ctx)}_{budget}"`). This prevents structural collisions in the leaf nodes of the deep spines, ensuring every branch of the large term remains unique.
