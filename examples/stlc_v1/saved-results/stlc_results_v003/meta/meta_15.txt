# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

*   **Asymmetric Budget Splitting (70/30 Ratio)**: The current best program (**Generation 7**, score 12.71) and high-performing variants like **Generation 13** (score 12.49) and **Generation 14** (score 12.67) utilize a 70/30 or 75/25 budget split in `AppTm` nodes. By allocating the majority of the budget (70%+) to the function side, these generators create deep, left-leaning application spines, which significantly boosted `tm_sizes_average` to 61.28 in the best program.
*   **High-Probability Variable Reuse in Base Cases**: The most successful programs (**Generation 7 and 8**) implement a "soft" base case where, if the budget is low ($\le 2$), they prioritize selecting a type-matching variable from the context with a 90% probability. This strategy directly correlates with the high `used_vars_proportions_average` (0.30) and ensures a 1.00 `good_ratio` by avoiding complex node generation when resources are depleted.
*   **Minimalist Intermediate Type Generation**: To maintain validity during application generation, the best program (**Generation 7**) and **Generation 12** (score 12.21) use a very small, restricted budget (e.g., `rng.randint(1, 2)`) for the argument type `arg_ty`. This ensures that the argument term remains simple enough to be generated within its 30% budget allocation, preventing the "generation cliff" where complex required types cannot be satisfied.
*   **Type-Directed Lambda Prioritization**: Programs that achieve high `applied_lambdas_proportions_average` (e.g., **Generation 12** at 0.86 and **Generation 14** at 0.78) explicitly check if the `target_ty` is a `FunTy`. If so, they prioritize generating a `LamTm` before attempting other constructors. This ensures that the functional structure of the STLC is fully utilized.

## Ineffective Approaches

*   **Symmetric Budget Distribution**: Programs that split budget 50/50 between the function and argument in an application (seen in earlier iterations like **Generation 5**) produce "bushy" but shallow trees. This limits the `tm_sizes_average` to ~17.00, significantly lower than the 61.28 achieved by the asymmetric approach in **Generation 7**.
*   **Unconstrained Argument Type Complexity**: As evidenced by **Generation 1**, allowing the generator to "invent" complex intermediate types for applications without a strict budget cap leads to a catastrophic failure in the `good_ratio` (0.03). If the required type is too complex, the recursive `gen_term` call for the argument is likely to fail within its remaining budget.
*   **Aggressive Redex Generation at the Expense of Size**: **Generation 10** achieved a high `applied_lambdas_proportions_average` (0.78) but a low total score (7.21) because its budget management was too restrictive, leading to an average term size of only 17.51. This indicates that redex density must be balanced with overall structural depth.

## Implementation Insights

*   **Correct-by-Construction Variable Selection**: The current best program (**Generation 7**) filters the context by type (`[name for name, ty in ctx if ty == target_ty]`) before making a selection. This ensures 100% validity while maximizing the `used_vars_proportions_average`.
*   **Budget-Aware Fallbacks**: The effectiveness of the best program lies in its "Hard Floor" logic. When the budget is $\le 2$, it strictly returns a variable or a literal. This prevents the generator from attempting to start an `App` or `Lam` node that it cannot possibly finish, maintaining a perfect `good_ratio`.
*   **Dynamic Context Naming**: Using `f"v{len(ctx)}"` for variable names (used in **Generations 7, 11, and 14**) prevents name collisions and allows the variable usage to scale naturally with the depth of the term, contributing to the high `unique_subterms_proportions_average` (0.99).
*   **Targeted Type vs. Term Budgeting**: The best program generates a target type with a small budget (10) and the term with a large budget (100). This discrepancy ensures the "goal" (the type) is simple enough to be inhabited, while the "solution" (the term) has enough "fuel" to become complex and unique.

## Performance Analysis

*   **The Size-Validity Tradeoff**: **Generation 7** represents the current performance ceiling (12.71) by successfully scaling `tm_sizes_average` to 61.28 without sacrificing the 1.00 `good_ratio`. Previous versions that attempted large sizes often saw validity drop.
*   **Correlation between Asymmetry and Score**: There is a clear trend where increasing the asymmetry of the budget split (from 50/50 to 70/30 or 80/20) correlates with higher scores. **Generation 13** (70/30 split) scored 12.49, and **Generation 14** (75/25 split) scored 12.67, both approaching the best program's performance.
*   **Variable Usage as a Score Driver**: Once validity is stabilized at 1.00, the primary differentiator in scores becomes `used_vars_proportions_average`. **Generation 7**'s score of 12.71 is supported by a 0.30 variable usage rate, whereas programs with lower variable reuse (like **Generation 0**) struggle to break the 10.50 mark.
*   **Type Complexity vs. Term Complexity**: Most high-scoring programs (**Generations 11, 13, 14**) maintain a relatively low `ty_sizes_average` (3.20 - 3.40). This suggests that the most efficient way to maximize the combined score is to generate complex terms for relatively simple types, rather than attempting to generate complex terms for complex types.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Implement "Context-Aware" Argument Type Selection**: Instead of generating a random `arg_ty` for `AppTm` using `gen_type(1, 2)`, prioritize selecting a type that already exists in the current `ctx`. By choosing an `arg_ty` from the types of available variables, you significantly increase the probability that the argument side of the application can be a `VarTm`, which will further boost the `used_vars_proportions_average` (currently 0.30) and ensure the 30% budget allocated to the argument is used efficiently.

2. **Introduce a "Beta-Redex" Generation Mode**: To improve the `applied_lambdas_proportions_average` (currently 0.48) without sacrificing term size, modify the `AppTm` logic to occasionally force the function side to be a `LamTm`. When generating the function part of an application, pass a boolean flag that increases the probability of choosing the `Lam` constructor; this creates immediate `(\x. M) N` structures, increasing both structural density and the complexity of the data flow.

3. **Dynamic Budget Reallocation for Variable-Rich Branches**: The current 70/30 asymmetric split is highly effective, but it can be refined by checking the `ctx` size. If the context is large (e.g., `len(ctx) > 5`), increase the probability of choosing a `VarTm` even at higher budgets (e.g., `budget <= 5`) and reallocate the "saved" budget from that leaf node back into other recursive branches to push the `tm_sizes_average` beyond the current 61.28.

4. **Scale Literal Diversity with Depth**: To maintain the high `unique_subterms_proportions_average` (0.99) as terms grow larger, replace fixed literal choices (like `["a", "b", "c"]`) with depth-dependent or budget-dependent generators. For example, use `f"v_{budget}_{len(ctx)}"` for strings or `rng.randint(0, 10**depth)` for integers; this ensures that even as the generator produces more nodes, the likelihood of subterm collisions remains near zero.

5. **Implement Type-Safe "Shadowing" Preference**: Modify the `valid_vars` selection to use a weighted choice that favors variables added more recently to the `ctx` (the end of the list). Since these variables correspond to inner scopes, prioritizing them mimics realistic code patterns where local variables are used more frequently than global ones, likely increasing the `used_vars_proportions_average` and creating more complex nested dependencies.
