# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

*   **Extreme Asymmetric Budget Splitting (98/2):** The current best program (**Asymmetric 98/2 Splitting with Manual Beta-Redex Injection**, score **13.91**) demonstrated that pushing the budget split beyond 95/5 to 98/2 significantly increases term size. This program achieved a `tm_sizes_average` of **200.20**, nearly double that of previous high-performers like **Generation 46** (112.94), while maintaining perfect validity.
*   **Manual Beta-Redex Injection (App-Lam Structure):** Forcing an `App(Lam, ...)` structure rather than relying on stochastic generation is the most effective way to maximize the `applied_lambdas_proportions_average`. Programs like **Generation 49** and **Generation 46** achieved scores of **0.89** and **0.86** respectively by explicitly constructing applied lambda terms when the budget is high (e.g., > 40).
*   **Context-Driven Argument Selection:** High-performing programs (**Generations 48 and 49**) prioritize selecting `arg_ty` from the existing context (`rng.choice(ctx)[1]`). This ensures that the argument side of an application can be satisfied by a `VarTm`, which preserves the majority of the budget for the function spine and simultaneously boosts the `used_vars_proportions_average` to **0.80**.
*   **Recent-Variable Shadowing Bias:** Selecting the most recently added variable from the context (`matches[-1]`) is a consistent pattern in programs achieving a **1.00 good_ratio**. This technique, used in **Generation 49** and **Generation 47**, ensures that even with massive term sizes and deep nesting, variable resolution remains stable and type-safe.

## Ineffective Approaches

*   **Symmetric or Moderate Budget Splitting:** Programs that do not use extreme asymmetry fail to reach the 100-node average size target. Even a 92/8 split (seen in earlier **Generation 42**) only achieved a size of **68.22**, which is significantly lower than the **200.20** achieved by the 98/2 split in **Generation 49**.
*   **Low Initial Fuel:** Using an initial fuel under 400 (as seen in **Generation 42**) limits the "surface area" for both variable reuse and beta-redex injection. The current best programs all utilize a fuel of **500**, which provides enough recursive depth to saturate the size and complexity metrics.
*   **Random Type Generation for Arguments:** Generating a completely new type for the argument of an application (rather than picking from the context) often leads to "dead ends" where the generator must create new literals or complex sub-terms to satisfy the type, wasting budget and lowering the `used_vars` proportion. **Generation 48** improved its score to **13.87** specifically by moving away from this and picking types directly from the context.

## Implementation Insights

*   **High-Entropy Naming and Literals:** The current best program (**Generation 49**) and **Generation 46** use `rng.getrandbits` (up to 30 bits) and string interpolation with `len(ctx)` to ensure that every sub-term is unique. This is the primary driver behind the perfect **1.00 unique_subterms_proportions_average** across all top-tier programs.
*   **Structural Lambda Forcing:** To maximize the `applied_lambdas` metric, the best programs (**Generations 45-49**) do not just generate lambdas for `FunTy`; they specifically force a `LamTm` into the function position of an `AppTm`. **Generation 49** achieved the highest metric (0.89) by combining this with the 98/2 split.
*   **Hard-Floor Variable Preference:** Implementing a 98% probability to return a `VarTm` when the budget is low (<= 2) is critical. This "hard floor" ensures that the ends of the deep spines created by the asymmetric split contribute to the `used_vars` metric rather than generating more literals.

## Performance Analysis

*   **The 13.91 Ceiling:** Both **Generation 46** and **Generation 49** achieved the peak score of **13.91**. However, **Generation 49** is arguably superior as it achieved a much higher `tm_sizes_average` (**200.20** vs **112.94**) and a higher `applied_lambdas_proportions_average` (**0.89** vs **0.86**) by using the 98/2 split.
*   **Correlation Between Size and Reuse:** There is a clear positive correlation between term size and variable reuse. **Generation 49**, with the largest terms (200.20), also achieved the highest variable reuse proportion (**0.80**), compared to **Generation 48** (size 112.44, reuse 0.78).
*   **Metric Saturation:** The `unique_subterms_proportions_average` and `good_ratio` have effectively been "solved" (staying at 1.00) by high-entropy naming and context-aware matching. The remaining competitive differentiation occurs in the balance between `used_vars` and `applied_lambdas`.
*   **Impact of Asymmetry on Depth:** The shift from 95/5 (**Generation 48**) to 98/2 (**Generation 49**) budget splitting resulted in a significant jump in term size without sacrificing validity, proving that the STLC structure can handle extreme left-heavy nesting if the variable selection logic is robust.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Push Asymmetric Spine Splitting to 98/2:** The jump from 95/5 to 98/2 in the most recent high-performer nearly doubled the `tm_sizes_average` from 112 to 200. Formally adopting this 98/2 split across all application nodes will ensure the generator consistently hits the 100-node target while leaving just enough budget (2%) for the argument branch to be satisfied by a single `VarTm` or literal.

2. **Implement Dynamic Beta-Redex Injection Scaling:** Currently, Beta-Redex Injection is fixed at a 35% trigger rate for budgets over 40. To maximize the `applied_lambdas_proportions_average` beyond 0.89, implement a scaling probability where the injection rate increases as the budget decreases (e.g., `0.3 + (1.0 - current_budget/500) * 0.6`). This ensures that as the term approaches its size limit, it more aggressively converts remaining nodes into applied lambdas.

3. **Introduce "Double-Lambda" Abstraction for Nested Types:** In the "Lambda Forcing" phase, instead of a single 92% chance to return a `LamTm`, implement logic that checks if the `target_ty` is a nested function (e.g., `Fun(A, Fun(B, C))`). If so, generate two nested lambdas in a single step; this increases the variable density of the context more rapidly, providing more fodder for the 98% context-aware variable reuse logic and boosting `used_vars_proportions_average`.

4. **Weight Context Selection by Type Frequency:** While the current program uses `rng.choice(ctx)[1]` to select argument types, it treats all types in the context equally. Weighting the selection toward types that appear most frequently in the context will increase the probability that the recursive `gen_term` call for the argument branch can be satisfied by a `VarTm` (via the 98% terminal match logic), pushing the `used_vars_proportions_average` toward 0.85.

5. **Context-Length Dependent Literal Salt:** To maintain the 1.00 `unique_subterms_proportions_average` as terms become even more complex (reaching 200+ nodes), move beyond simple random bits by incorporating the hash of the current context length and target type into literal values. Using `f"s_{len(ctx)}_{hash(str(target_ty))}_{rng.getrandbits(20)}"` ensures that even if the same variable name is reused in different branches, the terminal literals remain globally unique, preventing structural collisions in the subterm count.
