# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

*   **Aggressive Asymmetric Budget Splitting (92/8 Ratio):** The current best program (**Generation 30**, score 13.37) pushed the asymmetric split to a 92/8 ratio, surpassing the 90/10 split used in **Generation 28** (score 13.34). This extreme bias toward the function branch of an `AppTm` is the primary driver for increasing `tm_sizes_average` from 58.45 to 64.09, creating deep, left-heavy spines that maximize structural complexity.
*   **Frequency-Weighted Context Selection:** Prioritizing argument types that already exist in the context has proven to be the most effective way to boost variable reuse. **Generation 30** and **Generation 28** both utilized this "Inhabitant-Preference" strategy, achieving `used_vars_proportions_average` of 0.66 and 0.69 respectively. By selecting `arg_ty` from `[t for _, t in ctx]`, the generator ensures that the argument branch has a high probability of terminating with a `VarTm`.
*   **Over-Allocated Initial Budgets (250+):** Increasing the initial budget significantly beyond the target node limit (from 160 in Gen 22 to 250 in Gen 30) allowed the generators to approach the 100-node limit more effectively. This "budget scaling" strategy, combined with a robust "Hard Floor" base case, allows for massive terms (64.09 average size) while maintaining a 1.00 `good_ratio`.
*   **High-Probability Lambda Forcing (82-85%):** Forcing `LamTm` whenever the `target_ty` is a `FunTy` remains essential for balancing the `applied_lambdas_proportions`. **Generation 30** used an 82% threshold to achieve a 0.76 proportion, while **Generation 28** used a similar strategy to reach 0.81, demonstrating that this threshold is critical for maintaining lambda density in deep application spines.

## Ineffective Approaches

*   **Conservative Budget Splitting (75/25 or lower):** Earlier generations (Gen 19-21) that used more balanced budget splits failed to generate terms larger than 25 nodes. The feedback from **Generation 21** (score 12.54) specifically noted that conservative budget depletion logic failed to utilize the full "fuel" available, resulting in significantly lower scores compared to the asymmetric approaches of later generations.
*   **Random Argument Type Generation:** Generators that did not filter or bias `arg_ty` selection based on the current context (early iterations) suffered from lower `used_vars_proportions`. Without the "Context-Aware" selection seen in **Generation 30**, the probability of an argument branch being able to use a variable from the context drops significantly, forcing the generator to rely on literals.
*   **Low Initial Budgets:** Programs using budgets under 150 (Gens 20-25) were unable to break the 40.0 `tm_sizes_average` threshold. Even with efficient splitting, a low starting "fuel" limits the maximum possible depth of the term spine.

## Implementation Insights

*   **Shadowing-Preference Variable Selection:** The most successful programs (**Generation 30**, **Generation 28**, and **Generation 27**) all implement a "most-recent" variable selection strategy (`matches[-1]`). This prioritizes variables from the most local scopes, which is essential for maintaining high variable utilization (0.66+) in deeply nested lambda abstractions.
*   **Dynamic Variable Naming via Context Length:** Using `f"v{len(ctx)}"` (Gens 24-30) ensures unique identifiers for every abstraction. This implementation detail is responsible for the consistently high `unique_subterms_proportions_average` (0.97-0.98), as it prevents structural collisions that would occur with a fixed set of variable names.
*   **Identity-Like Small Budget Fallback:** In **Generation 30**, when the budget is small (<=3) but the `target_ty` is a `FunTy`, the generator creates a `LamTm` that immediately recurses. This ensures that even as the budget runs out, the generator attempts to satisfy function types structurally rather than failing or producing invalid terms.
*   **Type-Inhabitant Caching/Filtering:** The current best program (**Generation 30**) uses a 0.88 probability to pick an `arg_ty` from the context. This creates a self-reinforcing loop where the generator creates applications for types it knows it can satisfy, which is the key differentiator for its 13.37 score.

## Performance Analysis

*   **The 13.3+ Score Plateau:** **Generation 30** (13.37) and **Generation 28** (13.34) represent the current performance ceiling. The transition from 13.0 to 13.3 was primarily driven by increasing the `tm_sizes_average` from 35 to 64 while holding `good_ratio` at 1.00.
*   **Size vs. Variable Reuse Trade-off:** While **Generation 28** had higher variable reuse (0.69) than **Generation 30** (0.66), **Generation 30** scored higher overall due to its significantly larger average term size (64.09 vs 58.45). This indicates that at this stage of optimization, gains in raw term size are outweighing marginal gains in variable utilization.
*   **Consistency of Unique Subterms:** Across all top-performing programs (Gens 24-30), the `unique_subterms_proportions_average` remained stable at 0.97. This suggests that the current strategies for asymmetric splitting and unique variable naming are highly effective at avoiding redundant AST structures.
*   **Correlation between Budget and Complexity:** There is a direct linear correlation between the initial budget (160 -> 250) and the resulting `tm_sizes_average` (35 -> 64), provided the generator uses an aggressive (90%+) asymmetric split to prevent the budget from being distributed too thinly across many shallow branches.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Implement "Beta-Redex" Injection in Applications**: To push the `applied_lambdas_proportions_average` beyond the current 0.76, explicitly force the function side of an `AppTm` to be a `LamTm` with a 20-30% probability. This creates immediate `((\v. body) arg)` structures, which not only increases the lambda metric but also creates more local scopes for the "Inhabitant-Preference" logic to exploit, potentially breaking the 13.37 score barrier.

2. **Dynamic Tapered Budget Splitting**: While the 92/8 split is highly effective for size, it can "starve" argument branches, leading to literals. Implement a dynamic split that starts at 95/5 for the first 10 levels of recursion to establish a massive spine, then shifts to 75/25 as the budget depletes; this "tapering" should increase `tm_sizes_average` while providing more nodes for complex argument subtrees that can utilize variables.

3. **Context-Length Dependent Lambda Forcing**: Currently, lambda forcing is a fixed 82%. Scale this probability based on context size (e.g., `0.98` if `len(ctx) < 8`, decreasing to `0.60` as the context grows) to ensure that the generator aggressively builds a rich variable pool early in the term's generation, providing a larger "menu" of types for the deep spine to reference later.

4. **Frequency-Weighted Type Selection with Counter**: Refine the "Inhabitant-Preference" by using a frequency map of types in the context. Instead of a uniform `rng.choice` from the context, weight the selection of `arg_ty` toward types that appear most frequently; this increases the mathematical probability that the argument branch can satisfy its type requirement using a variable, pushing `used_vars_proportions_average` toward 0.70.

5. **Unique Literal Generation for Leaf Nodes**: To maintain the 0.97 `unique_subterms_proportions_average` as terms grow toward the 100-node limit, replace static literals like `"val"` or `1000` with dynamic values such as `f"s_{len(ctx)}_{budget}"` or `rng.randint(0, 10**9)`. This ensures that even when the "Hard Floor" is hit frequently in a large term, every leaf remains structurally distinct, preventing a drop in the uniqueness metric.
