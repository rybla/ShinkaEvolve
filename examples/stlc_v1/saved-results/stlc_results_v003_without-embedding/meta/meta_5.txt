# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

*   **Type-Directed Budget Splitting with Contextual Variable Injection**: The most successful programs (Generation 3 and 4) utilize a recursive budget-based approach where the target type dictates the term structure. Generation 4 achieved the highest score (12.64) by prioritizing lambda abstractions for function types and splitting the remaining budget between function and argument in `AppTm` nodes.
*   **Heuristic-Based Variable Selection**: Prioritizing the selection of variables from the typing context (`gamma`) over generating new literals is crucial for increasing complexity. Generation 4 improved upon Generation 3 by using a 70% probability to pick a valid variable from the context when the budget is low, contributing to its superior `tm_sizes_average` of 80.91.
*   **Dynamic Argument Type Generation for Applications**: To successfully generate `AppTm` nodes, the generator must invent an intermediate type `A` for a function `A -> B`. Generation 4's strategy of using a small, dedicated budget (`rng.randint(1, 3)`) for these intermediate types ensures they remain simple enough to be satisfied by the recursive `gen_term` call, maintaining a 1.00 `good_ratio`.
*   **Depth-Limited Recursion with Base-Case Fallbacks**: Successful programs (Generation 0, 3, and 4) use a depth or budget counter to force terminal nodes (Literals or Variables). Generation 0 achieved a 1.00 `good_ratio` by switching to base types at a specific depth, though it lacked the structural complexity found in Generation 4.

## Ineffective Approaches

*   **Unconstrained Intermediate Type Generation**: Generation 1 (`stlc_recursive_generator`) failed significantly (score 2.51, `good_ratio` 0.03) because its `AppTm` logic generated intermediate types that the recursive calls could not satisfy within the remaining budget, leading to frequent generation failures.
*   **Lack of Robust Type-Safety Checks**: Generation 2 (`stlc_generator_with_context`) achieved a decent score (8.32) but failed validation because it lacked a "guaranteed" terminal case for complex types when the budget was depleted, resulting in a 64% validity ratio.
*   **Shallow Recursion without Variable Usage**: Generation 0, while perfectly valid, produced "repetitive, shallow structures" and failed to utilize variables (`used_vars_proportions_average` of 0.00). This demonstrates that validity alone does not lead to high scores if structural complexity and variable reuse are ignored.

## Implementation Insights

*   **Context Management via Symbol Tables**: The current best program (Generation 4) maintains a list of `(name, type)` tuples. This allows it to filter `valid_vars` that match the `target_ty` exactly, ensuring type correctness while attempting to increase the `used_vars_proportions_average`.
*   **Balancing Lambda and Application Probabilities**: Generation 4 uses a 60% probability to generate a `Lam` when the target is a `FunTy`. This specific weighting, combined with budget splitting, allows it to reach an average term size of 80.91, which is nearly 10x larger than Generation 3 (8.10).
*   **String-Based Variable Indexing**: Using `f"v{len(ctx)}"` (as seen in Generation 3 and 4) provides a simple, collision-free way to manage variable names in the nested scope, which is essential for valid `LamTm` construction.
*   **Budget-Aware Literal Generation**: The best program ensures that if the budget is $\le 1$, it *must* return a variable or a literal. This "hard floor" on recursion is what separates the 1.00 `good_ratio` programs from the failing ones like Generation 2.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Implement Context-Aware Intermediate Type Selection for Applications**: Instead of generating a random intermediate type `A` for `AppTm` nodes using `gen_type`, prioritize types that already exist within the current typing context (`ctx`). By selecting an `arg_ty` from the types of variables already available, you significantly increase the probability that the argument term `x` can be a simple `VarTm`, which will improve both the `used_vars_proportions_average` and the likelihood of successful term completion.

2. **Introduce "Shadowing-Safe" Variable Frequency Weighting**: To address the low `used_vars_proportions_average` (0.21), modify the variable selection logic to use a weighted choice that favors the most recently added variables in the context. Since inner-scope variables are often more relevant to the current sub-expression, prioritizing them (while maintaining type-safety) will lead to more meaningful variable usage and deeper data-flow dependencies within the generated terms.

3. **Refine Budget Splitting with Asymmetric Allocation**: The current 50/50 budget split in `AppTm` is effective but can be improved by allocating more budget to the function side (`f`) when the target type is complex, and more to the argument side (`x`) when the argument type is complex. Implementing a `split = budget - k` where `k` is a small constant for the argument (or vice versa) can help generate deeply nested function chains like `f x y z` which are common in functional programming.

4. **Add a "Beta-Reduction" Bias to Application Nodes**: To increase the `applied_lambdas_proportions_average` and `unique_subterms_proportions_average`, explicitly increase the probability that the function side of an `AppTm` is a `LamTm`. When generating `gen_term(fun_ty, ctx, split)`, pass a flag or increase the internal probability for `Lam` generation, forcing the creation of immediate redexes (`(\x. M) N`), which increases structural density and complexity.

5. **Implement Type-Driven Literal Constraints**: Enhance the `gen_term` base cases to produce more diverse literals based on the depth of the tree. For example, instead of `rng.randint(0, 100)`, use the current `budget` or `depth` to scale the magnitude of integers or the length of strings. This ensures that even terminal nodes contribute to the `unique_subterms_proportions_average` and prevents the generator from producing identical leaf nodes across different branches.
