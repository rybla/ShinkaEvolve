# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

*   **Asymmetric Budget Splitting for Application Depth**: The current best program (**Generation 7**, score 12.71) significantly outperformed previous versions by allocating 70% of the budget to the function side of `AppTm` nodes. This specific ratio allows for deeper application chains and more complex functional structures, resulting in a `tm_sizes_average` of 61.28, compared to the ~17.00 seen in **Generations 5, 6, and 10** which used more balanced or less aggressive splitting.
*   **Type-Safe Variable Prioritization with High Probability**: Successful programs (**Generation 7 and 8**) prioritize selecting matching variables from the context (`ctx`) when the budget is low. **Generation 7** uses a 90% probability to pick a valid variable if the budget is $\le 2$, which contributed to its high `used_vars_proportions_average` of 0.30 and a perfect 1.00 `good_ratio`.
*   **Small-Scale Intermediate Type Generation**: To generate an application `(f x)`, the generator must invent a type for `x`. The most successful programs (**Generation 7 and 4**) use a very small, fixed budget (e.g., `rng.randint(1, 2)`) for these intermediate types. This ensures the argument `x` remains simple enough to be generated within the remaining term budget, maintaining validity while allowing the function `f` to be complex.
*   **Context-Aware Lambda Generation**: Prioritizing `LamTm` when the target type is a `FunTy` (used in **Generations 6, 7, and 10**) ensures that the generated terms reflect the functional nature of the calculus. **Generation 10** achieved the highest `applied_lambdas_proportions_average` (0.78) by aggressively prioritizing lambdas, though it sacrificed total term size.

## Ineffective Approaches

*   **Early Termination via Literals**: **Generation 5** and **Generation 10** suffered from low average term sizes (17.07 and 17.51 respectively) because their budget distribution logic or recursive calls consumed the budget too quickly or defaulted to literals too early. This prevents the generator from reaching the structural complexity seen in **Generation 7**.
*   **Unconstrained Intermediate Types**: As seen in **Generation 1**, generating complex intermediate types for applications without a restricted budget leads to a "generation cliff" where the recursive call for the argument fails to find a valid term, resulting in a catastrophic `good_ratio` (0.03).
*   **Symmetric or Random Budget Splitting**: Programs that split budget 50/50 or randomly between function and argument often produce "bushy" but shallow trees. **Generation 7** proved that favoring the function side (70/30 split) is superior for generating the deep nested structures characteristic of complex lambda terms.

## Implementation Insights

*   **The "Hard Floor" for Recursion**: The current best program (**Generation 7**) ensures 100% validity by implementing a strict base-case fallback: if the budget is $\le 2$, it *must* return either a valid variable from the context or a literal. This prevents the generator from attempting complex nodes (like `App`) when it lacks the resources to complete them.
*   **Dynamic Context Growth**: By using `f"v{len(ctx)}"` for new variable names, the best programs (**Generations 4, 7, and 8**) create a unique, stack-like naming convention that avoids collisions and allows the `used_vars_proportions_average` to scale with term depth.
*   **Targeted Type Generation**: **Generation 7** generates a target type with a small budget (10) before generating the term with a large budget (100). This ensures the "goal" is achievable while providing enough "fuel" for the term generator to create a large, unique AST (0.99 uniqueness).
*   **Filtering Context by Type**: The efficiency of **Generation 7** and **8** stems from filtering the context (`valid_vars = [name for name, ty in ctx if ty == target_ty]`) before making a generation decision. This ensures that every variable selection is "correct by construction."

## Performance Analysis

*   **The Complexity Ceiling**: **Generation 7** currently holds the highest score (12.71), demonstrating that the combination of asymmetric splitting and high-probability variable reuse is the most effective way to balance `tm_sizes_average` (61.28) with `good_ratio` (1.00).
*   **Variable Usage Correlation**: There is a direct link between `used_vars_proportions_average` and the final score. **Generation 0** (0.00 vars) scored 10.28, while **Generation 7** (0.30 vars) reached 12.71. Increasing variable reuse is the primary driver for higher scores once validity is stabilized.
*   **Redex Density**: **Generation 10** achieved a very high `applied_lambdas_proportions_average` (0.78), but its lower term size (17.51) resulted in a lower overall score (7.21). This indicates that while creating redexes is important, it cannot come at the expense of total term volume and depth.
*   **Consistency vs. Complexity**: **Generation 6** (score 10.84) and **Generation 7** (score 12.71) both achieved high validity, but the ~4x increase in term size in **Generation 7** (from 16.89 to 61.28) highlights that budget management is the most sensitive lever for performance optimization in this generator.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Implement "Context-Driven" Argument Type Selection**: Instead of generating a random `arg_ty` for `AppTm` using `gen_type(rng.randint(1, 2))`, prioritize selecting a type that already exists in the current `ctx`. By choosing an `arg_ty` from the types of available variables, you significantly increase the probability that the argument side of the application can be a `VarTm`, which will further boost the `used_vars_proportions_average` and ensure the 30% budget allocated to the argument is used efficiently.

2. **Introduce a "Beta-Redex" Generation Mode**: To improve the `applied_lambdas_proportions_average` (currently 0.48) without sacrificing term size, modify the `AppTm` logic to occasionally force the function side to be a `LamTm`. When generating the function part of an application, pass a boolean flag that increases the probability of choosing the `Lam` constructor; this creates immediate `(\x. M) N` structures, increasing both structural density and the complexity of the data flow.

3. **Dynamic Budget Reallocation for Variable-Rich Branches**: The current 70/30 asymmetric split is highly effective, but it can be refined by checking the `ctx` size. If the context is large (e.g., `len(ctx) > 5`), increase the probability of choosing a `VarTm` even at higher budgets (e.g., `budget <= 5`) and reallocate the "saved" budget from that leaf node back into other recursive branches to push the `tm_sizes_average` beyond the current 61.28.

4. **Scale Literal Diversity with Depth**: To maintain the high `unique_subterms_proportions_average` (0.99) as terms grow larger, replace fixed literal choices (like `["a", "b", "c"]`) with depth-dependent or budget-dependent generators. For example, use `f"v_{budget}_{len(ctx)}"` for strings or `rng.randint(0, 10**depth)` for integers; this ensures that even as the generator produces more nodes, the likelihood of subterm collisions remains near zero.

5. **Implement Type-Safe "Shadowing" Preference**: Modify the `valid_vars` selection to use a weighted choice that favors variables added more recently to the `ctx` (the end of the list). Since these variables correspond to inner scopes, prioritizing them mimics realistic code patterns where local variables are used more frequently than global ones, likely increasing the `used_vars_proportions_average` and creating more complex nested dependencies.
