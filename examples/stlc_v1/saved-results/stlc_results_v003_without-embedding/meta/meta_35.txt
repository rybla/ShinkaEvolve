# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

*   **Ultra-Aggressive Asymmetric Budget Splitting (94/6 Ratio):** The current best program (**Generation 34**, score 13.68) achieved the highest `tm_sizes_average` (91.13) by pushing the asymmetric split to a 94/6 ratio. This surpasses the 92/8 ratio used in **Generations 29, 31, 32, and 33** (scores 13.28–13.53). This extreme bias toward the function branch of an `AppTm` is the primary driver for maximizing term depth and size while staying within the 100-node limit.
*   **Context-Weighted Type Selection for Arguments:** The most successful programs (**Generation 34** and **Generation 33**) prioritize selecting `arg_ty` for applications from types already present in the context (`rng.choice([t for _, t in ctx])`). This "Inhabitant-Preference" strategy ensures that the argument branch of an application can be satisfied by a `VarTm`, leading to a `used_vars_proportions_average` of 0.71 in **Generation 34**, compared to lower scores in programs that relied more on random type generation.
*   **High-Probability Lambda Forcing (85-98%):** To maintain high `applied_lambdas_proportions`, top-performing programs aggressively force `LamTm` when the `target_ty` is a `FunTy`. **Generation 29** used a 98% probability, while **Generation 34** used 85% to achieve a 0.80 proportion. This ensures that deep spines are populated with abstractions rather than just applications of literals.
*   **Extreme Initial Budgeting (280-400):** There is a direct correlation between the initial "fuel" and the final term size. **Generation 34** utilized an initial budget of 400 to reach an average size of 91.13, while **Generation 32** used a budget of 280 to reach a size of 66.85. Over-allocating budget relative to the 100-node limit allows the generator to "spend" more on deep branches before hitting the hard floor.

## Ineffective Approaches

*   **Lower Asymmetric Ratios (90/10 and below):** While 90/10 was successful in earlier iterations (Gen 28), it has been superseded by the 92/8 and 94/6 splits. Programs using the 92/8 split (like **Generation 29**) achieved sizes around 65.14, which is significantly lower than the 91.13 achieved by the 94/6 split in **Generation 34**, indicating that even marginal increases in asymmetry yield substantial size gains.
*   **Random Literal Generation without Context Filtering:** Earlier generations that did not bias `arg_ty` selection toward existing context inhabitants suffered from lower variable reuse. Without the "Context-Aware" selection seen in **Generation 34**, the generator is forced to create new literals or complex subterms to satisfy application arguments, which reduces the `used_vars_proportions_average`.
*   **Conservative Initial Budgets:** Programs with budgets under 250 (Gens 20-25) were unable to break the 60.0 `tm_sizes_average` threshold. Even with efficient splitting, a low starting "fuel" limits the maximum possible depth of the term spine, as seen in the jump from **Generation 29** (Budget 250, Size 65.14) to **Generation 34** (Budget 400, Size 91.13).

## Implementation Insights

*   **Shadowing-Biased Variable Selection:** The current best program (**Generation 34**) and its predecessors (**Generation 33, 32**) implement a "most-recent" variable selection strategy (`matches[-1]`). By picking the most recently added variable that matches the target type, the generator maximizes local shadowing, which is essential for maintaining high variable utilization (0.71) in deeply nested structures.
*   **Hard Floor with Identity-Like Fallbacks:** **Generation 34** uses a "Hard Floor" logic (budget <= 3) that attempts to return a variable first (98% probability), then a literal, and finally a minimal `LamTm` if the type is a function. This ensures that even as the budget is exhausted, the generator maintains type validity and high variable reuse.
*   **Dynamic Variable Naming via Context Length:** Using `f"v{len(ctx)}"` (as seen in **Generation 34**) ensures unique identifiers for every abstraction. This implementation detail is responsible for the consistently high `unique_subterms_proportions_average` (0.97), as it prevents structural collisions that would occur with a fixed set of variable names.
*   **Frequency-Weighted Context Selection:** The logic `arg_ty = rng.choice([t for _, t in ctx])` creates a self-reinforcing loop where the generator creates applications for types it knows it can satisfy with existing variables. This is the key differentiator for the 13.68 score in **Generation 34**.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Push Asymmetric Splitting to the Limit (96/4 Ratio):** Given that the jump from 92/8 to 94/6 was the primary driver for the record-breaking 91.13 average size, test a 96/4 or 97/3 split. This extreme bias further elongates the function spine of `AppTm` nodes, allowing the generator to utilize the 400-unit budget more effectively before hitting the 100-node hard limit, potentially pushing `tm_sizes_average` toward 95+.

2. **Implement Explicit Beta-Redex Injection:** To increase the `applied_lambdas_proportions_average` from 0.80 toward 0.90, modify the `AppTm` generation logic to occasionally (e.g., 25% of the time) force the function branch to be a `LamTm` regardless of the budget. This creates `((\v. body) arg)` structures which guarantee an applied lambda and provide a fresh variable in the context for the body of the application's function side.

3. **Context-Aware Type Selection with "Freshness" Bias:** Refine the current inhabitant-preference logic by weighting the `rng.choice([t for _, t in ctx])` toward types that were added most recently to the context. Since the generator uses a "most-recent" variable selection strategy (`matches[-1]`), biasing the `arg_ty` selection toward recent types will create a tighter loop of variable reuse, likely increasing the `used_vars_proportions_average` beyond 0.71.

4. **Dynamic Budget-Based Lambda Forcing:** Instead of a fixed 85% probability for forcing lambdas, scale this probability based on the remaining budget (e.g., `0.95` if `budget > 100`, dropping to `0.50` as `budget` approaches 0). This ensures that the generator aggressively builds a deep, variable-rich environment during the early "spine-building" phase, while allowing more variety and terminal nodes as the budget depletes.

5. **Structural Uniqueness via Context-Length Literals:** To protect the 0.97 `unique_subterms_proportions_average` as terms become even larger, ensure every leaf node is globally unique by incorporating both the current context length and the current budget into literal values (e.g., `f"s_{len(ctx)}_{budget}_{rng.getrandbits(16)}"`). This prevents structural collisions in the "Hard Floor" logic where multiple branches might otherwise return identical terminal constants or variables.
