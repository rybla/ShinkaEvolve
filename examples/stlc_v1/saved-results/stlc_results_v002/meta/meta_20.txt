# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

*   **Simultaneous Type-Term Co-generation with Depth Control**: The current best program (Score: 10.30) and Generation 23 (Score: 10.29) utilize a recursive strategy that generates a type and its corresponding term in a single step. By using `rng.randrange(0, 4 if depth > 0 else 3)`, these programs ensure recursion terminates into base literal types (`Bool`, `Int`, `String`) once the depth limit is reached, maintaining a perfect 1.00 `good_ratio`.
*   **Identity-Style Lambda Wrapping**: High-scoring programs (Best Program, Gen 23, Gen 25) use a pattern where a recursive call is wrapped in a `Lam` constructor. For example, the best program returns `(("Fun", ("Int",), ty), ("Lam", "x", ("Int",), tm))`. This guarantees structural validity and type-consistency without requiring a complex type-checker or environment tracker.
*   **Scope-Aware Variable Tracking**: Generation 21 (Score: 9.11) successfully implemented a `bound_vars` list to track scope. While its overall score was lower due to smaller term sizes, it achieved a `used_vars_proportions_average` significantly higher than the 0.00 seen in the best program by injecting variable references from the tracked scope into the term body.
*   **Hardcoded Literal Leaf Nodes**: All programs with a `good_ratio` of 1.00 (Generations 20, 22, 23, 25, and the Best Program) rely on fixed, valid constants like `("Int", 27)` or `("Bool", True)`. This ensures that the base cases of the recursion always satisfy the `LitTm` and `Ty` aliases.

## Ineffective Approaches

*   **Static Variable Usage without Environment Tracking**: The current best program and Generations 20, 22, 23, and 25 all suffer from a `used_vars_proportions_average` of 0.00. Using a variable name like `"x"` in a `Lam` but failing to insert a corresponding `('Var', 'x')` term in the body prevents the generator from exploring the logic of the lambda calculus.
*   **Failure to Decrement Depth**: Generations 20 and 22 both contained logic where the `depth` parameter was passed to recursive calls but never decremented (e.g., `generate_sample(rng, depth)` instead of `depth - 1`). While they avoided stack overflows due to a random distribution favoring base cases, this flaw prevents intentional control over term complexity.
*   **Omission of the Application (`App`) Constructor**: The 10.30 score ceiling is largely due to the total omission of the `App` constructor. Programs like Gen 23 and Gen 25 achieved 1.00 `good_ratio` but 0.00 `applied_lambdas_proportions_average`, resulting in very low structural complexity (average size ~1.3).
*   **Type Mismatches in Complex Structures**: Generation 21 attempted `App` and `Lam` logic but resulted in a lower `good_ratio` (0.87) compared to the simpler generators. This indicates that as structural complexity increases, the risk of generating ill-typed terms (e.g., applying a non-function type) increases significantly if not managed by strict co-generation.

## Implementation Insights

*   **The "Correctness First" Strategy**: The current best program (Score 10.30) is effective because it prioritizes a 1.00 `good_ratio` over structural complexity. By using a narrow set of constructors (`LitTm` and `LamTm`) and ensuring the `Ty` and `Tm` structures match the aliases exactly, it avoids the validation failures that result in 0.0 scores.
*   **Tuple-Based Embedding Adherence**: The difference between a functional program and a 0.0 score is strict adherence to the `(Constructor, *Args)` format. The best program correctly nests the tuples: `("Fun", ("Int",), ty)`, whereas failing programs often struggle with the nested nature of `FunTy` and `LamTm`.
*   **Branching Factor vs. Term Size**: The best program uses a branching factor of 4 (3 literal types + 1 lambda type). This small branching factor, combined with the depth limit, results in an average term size of 1.38. Generation 21 attempted more complex branching but produced smaller terms (1.9) because its logic for `App` and `Lam` often defaulted to base cases to maintain safety.
*   **Hardcoded Parameter Types**: Generation 23 and the best program both use a fixed `"Int"` type for all lambda parameters: `("Lam", "x", ("Int",), tm)`. While this ensures type safety, it limits the diversity of the generated ASTs and contributes to the low `unique_subterms_proportions_average` (0.15).

## Performance Analysis

*   **The 10.30 Score Ceiling**: There is a persistent performance plateau at 10.30. The current best program reaches this limit by perfecting the `good_ratio` but failing to implement `App` terms or meaningful `Var` usage.
*   **Complexity-Correctness Trade-off**: Generation 21 (Score 9.11) attempted more complex variable naming and application logic but saw a drop in score compared to the best program (10.30) because its `good_ratio` fell to 0.87. This confirms that the scoring metric heavily rewards the reliability of the `good_ratio`.
*   **Metric Stagnation**: Across all "Correct" programs (Generations 20, 22, 23, 25, and the best), the `used_vars_proportions_average` remains at 0.00. This highlights a universal failure to link the variable defined in `Lam` to a `Var` term in the body.
*   **Impact of Term Size on Score**: Despite all having a 1.00 `good_ratio`, the best program (10.30) slightly outperforms Generation 22 (10.26) and Generation 25 (10.28) due to marginally higher `tm_sizes_average` (1.38 vs 1.29 and 1.33 respectively), suggesting that even small increases in recursion depth or branching frequency improve the final score.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Implement Context-Aware Variable Injection**: To break the 0.00 `used_vars_proportions_average`, modify `generate_sample` to pass a `ctx` list of `(name, type)` tuples. When `depth` is low, add a weighted branch that selects a variable from `ctx` to return as a `VarTm`, ensuring the returned `Ty` matches the one stored in the context for that variable name.

2. **Introduce Type-Safe `App` via Function-First Generation**: To improve `applied_lambdas_proportions_average`, implement a branch that first generates a random function type `('Fun', arg_ty, ret_ty)`. Then, recursively generate a term for the function part (ensuring it matches `('Fun', arg_ty, ret_ty)`) and a term for the argument part (matching `arg_ty`), combining them into an `AppTm`.

3. **Transition to Depth-Decrementing Recursion**: The current best program fails to decrement `depth` in its recursive call (`generate_sample(rng)`), relying on random chance to terminate. Explicitly pass `depth - 1` to recursive calls to allow for a higher initial depth (e.g., 5-10) while guaranteeing termination and enabling more complex, nested structures.

4. **Diversify Lambda Parameter Types**: Instead of hardcoding `("Int",)` for all `LamTm` annotations, create a helper function `generate_type(rng, depth)` to produce varied types. This will increase `ty_sizes_average` and `unique_subterms_proportions_average` by allowing functions like `Bool -> Int` or `(Int -> Int) -> Int` instead of just nested `Int -> Int` chains.

5. **Apply Weighted Constructor Selection**: Replace the uniform `randrange` with a weighted selection (e.g., `rng.choices`) that favors `Lam` and `App` when `depth` is high and shifts weight toward `LitTm` and `VarTm` as `depth` approaches zero. This strategy maximizes `tm_sizes_average` while maintaining the 1.00 `good_ratio` by ensuring the generator "tapers off" into valid base cases.
