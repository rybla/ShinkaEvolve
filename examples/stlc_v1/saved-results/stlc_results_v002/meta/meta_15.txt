# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

- **Simultaneous Type-Term Co-generation with Depth Control**: The current best program (Score: 10.30) and Generation 19 (Score: 10.26) utilize a recursive strategy that generates a type and its corresponding term in a single step. By passing a `depth` parameter and using `rng.randrange(0, 4 if depth > 0 else 3)`, these programs ensure that recursion terminates into base literal types (`Bool`, `Int`, `String`) once the depth limit is reached, maintaining a 1.00 `good_ratio`.
- **Identity-Style Lambda Wrapping**: High-scoring programs (Generation 15, 19, and the current best) use a pattern where a recursive call is wrapped in a `Lam` constructor. For example, the best program returns `(("Fun", ("Int",), ty), ("Lam", "x", ("Int",), tm))`. This guarantees structural validity and type-consistency without requiring a complex type-checker or environment tracker.
- **Context-Free Variable Naming**: Generation 15 (Score: 7.11) introduced a dynamic naming convention based on recursion depth (`f"x{depth}"`). While this did not significantly boost the score compared to the best program's static `"x"`, it represents a successful step toward managing variable binding which is necessary for more complex terms.
- **Hardcoded Literal Leaf Nodes**: All programs with a `good_ratio` above 0.0 (Generations 15, 19, and the best program) rely on fixed, valid constants like `("Int", 27)` or `("Bool", True)`. This ensures that the base cases of the recursion always satisfy the `LitTm` and `Ty` aliases.

## Ineffective Approaches

- **Placeholder Logic and External References**: Generations 13, 16, and 17 all failed with a score of 0.0. These programs defined the `Ty` and `Tm` aliases but lacked a functional `generate_sample` implementation, often leaving comments or isolated expression blocks. This confirms that the evaluation environment requires a fully self-contained, executable generation function.
- **Conservative Recursion without Application**: While Generation 19 achieved a 1.00 `good_ratio`, its score (10.26) is slightly lower than the best program because it produced very small average sizes (1.29). It avoided the `App` (Application) constructor entirely, leading to zero `applied_lambdas_proportions_average`.
- **Static Variable Usage without Environment Tracking**: Even the "Correct" programs (Generations 15, 19, and the best program) suffer from a `used_vars_proportions_average` of 0.00 or near-zero (0.06 for Gen 15). Using a variable name in a `Lam` but failing to insert a corresponding `Var` term in the body prevents the generator from exploring the full logic of the lambda calculus.

## Implementation Insights

- **The "Correctness First" Strategy**: The current best program (Score 10.30) is effective because it prioritizes a 1.00 `good_ratio` over structural complexity. By using a narrow set of constructors (`LitTm` and `LamTm`) and ensuring the `Ty` and `Tm` structures match the aliases exactly, it avoids the validation failures that resulted in 0.0 scores for more ambitious but incomplete programs like Generation 16.
- **Recursive Branching vs. Linear Growth**: Generation 15 achieved a higher `used_vars_proportions_average` (0.06) than the best program (0.00) by attempting to track depth, but it resulted in a lower overall score (7.11) due to smaller average term sizes. This suggests that the current scoring metric heavily rewards the reliability of the `good_ratio` over minor increases in variable utilization.
- **Tuple-Based Embedding Adherence**: The difference between a functional program and a 0.0 score is strict adherence to the `(Constructor, *Args)` format. Failing programs (Gen 13, 17) often struggle with the nested nature of `FunTy` and `LamTm`, whereas the best program correctly nests the tuples: `("Fun", ("Int",), ty)`.

## Performance Analysis

- **The 10.30 Score Ceiling**: There is a persistent performance plateau at 10.30. Both the current best program and previous high-performers (like Generation 14) reach this limit by perfecting the `good_ratio` but failing to implement `App` terms or meaningful `Var` usage.
- **Complexity-Correctness Trade-off**: Generation 15 (Score 7.11) attempted more complex variable naming but saw a drop in score compared to the best program (10.30). This indicates that increasing complexity without maintaining the 1.00 `good_ratio` is detrimental to the combined score.
- **Metric Stagnation**: Across all "Correct" programs (Generations 15, 19, and the best), the `unique_subterms_proportions_average` remains low (0.15). This confirms that the current recursive strategies produce highly repetitive trees (e.g., nested identity functions) rather than diverse mathematical expressions.
- **Impact of Omitted Constructors**: The zero scores for `applied_lambdas_proportions_average` across all programs highlight a universal failure to implement the `App` constructor, which is the primary barrier to exceeding the 10.30 score threshold.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Implement a Context-Aware Variable Store for `VarTm` Generation**: To break the 0.00 `used_vars_proportions_average`, modify `generate_sample` to accept an optional `ctx` list of `(name, type)` tuples. When `depth` reaches 0, add a weighted chance to select a variable from this context and return its corresponding `VarTm` and `Ty`, rather than always defaulting to a literal.

2. **Introduce the `App` Constructor via Type-First Generation**: To improve `applied_lambdas_proportions_average`, implement a branch that first generates a random function type `('Fun', src, tgt)`. Then, recursively call the generator to produce a function term of that type and an argument term of type `src`, combining them into an `AppTm` to ensure the application is well-typed.

3. **Dynamic Type Generation for Abstractions**: Instead of hardcoding `("Int",)` as the domain for all `LamTm` constructors, create a helper function `generate_type(rng, depth)` that randomly produces `Bool`, `Int`, `String`, or `Fun` types. This will increase `ty_sizes_average` and ensure that the generated function spaces are more diverse than the current nested identity patterns.

4. **Unique Variable Naming with Depth-Based Indexing**: Replace the static variable name `"x"` with a unique identifier system, such as `f"v{depth}"` or a counter based on the context length, to avoid shadowing and allow for complex nested terms. This ensures that when a `VarTm` is selected from the context, it refers to a specific, valid binding site, which is essential for maintaining a high `good_ratio` while increasing term complexity.

5. **Weighted Selection for Structural Diversity**: Replace the `rng.randrange` logic with `rng.choices` using depth-dependent weights that favor `Lam` and `App` at high depths and `Lit` or `Var` at low depths. By decreasing the probability of recursive constructors as `depth` approaches zero, you can safely increase the initial depth limit to generate larger `tm_sizes_average` without risking infinite recursion or validation failures.
