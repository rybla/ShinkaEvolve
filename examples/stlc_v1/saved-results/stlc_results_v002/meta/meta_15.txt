# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

*   **Multi-Binder Redex Chaining**: The current best program (**Generation 14**, score 12.38) introduced "Redex-Chains" which explicitly construct nested applications of lambdas (e.g., `((\x. \y. body) arg1) arg2`). This technique, combined with a 25% trigger probability, maintained the high `applied_lambdas_proportions_average` of 0.62 while simultaneously pushing the `used_vars_proportions_average` to 0.40, the highest recorded for a valid program.
*   **Context-Inhabited Argument Selection**: A key driver for the 12.38 score in **Generation 14** was the strategy of picking `arg_ty` for an `App` node from the existing context (75% probability). This ensures that the argument branch can be satisfied by a `Var` node, directly increasing variable usage and ensuring the term remains well-typed even as complexity grows.
*   **Explicit Redex Injection with Budget Scaling**: Programs that hardcode the `App(Lam(...), ...)` structure (**Generations 10, 11, 12, and 14**) consistently outperform those that rely on random chance to form redexes. **Generation 12** achieved a score of 12.37 by using this method to reach a 0.62 applied lambda proportion. The best program (**Generation 14**) refined this by using `budget // 3` and `budget // 5` for sub-branches, preventing the 100-node limit violations seen in failed attempts.
*   **Targeted Callable Lookup**: Searching the context for variables of type `Fun` that specifically return the `target_ty` (used in **Generations 12 and 14**) ensures that applications are not just random structures but are functional paths to the required type. This "Medium Priority" logic in the best program helps maintain a 1.00 `good_ratio` despite high structural complexity.

## Ineffective Approaches

*   **Greedy Redex Injection without Budget Constraints**: **Generation 13** (score 9.08) failed because its "Greedy" approach to redex injection did not properly manage the 100-node limit. By attempting to wrap terms in applied lambdas without efficient budget splitting, it produced terms that either failed validation or exceeded size constraints, leading to its "Incorrect" status.
*   **Inefficient Budget Splitting in Recursive Applications**: Programs that use naive budget splitting (e.g., simply passing `budget - 1` to both sides of an `App`) often hit recursion limits or produce lopsided, invalid trees. **Generation 13**'s failure highlights that as the complexity of the injection strategy increases, the precision of the budget division (like the 60/35 split in **Generation 14**) becomes critical.
*   **Low Variable Utilization**: Earlier versions like **Generation 10** (score 12.14) focused heavily on the `applied_lambdas` metric but neglected `used_vars`. While valid, they achieved lower overall scores because they did not prioritize selecting argument types that were already present in the typing context.

## Implementation Insights

*   **Strategic Variable Naming and Context Tracking**: The best program (**Generation 14**) uses `f"v{len(ctx)}"` to ensure unique variable names while tracking context depth. This allows the "Redex-Chain" logic to inject multiple variables (`v1`, `v2`) and immediately utilize them in the generated body, maximizing the `used_vars` metric.
*   **Weighted Type Bias**: Consistently successful programs (**Generations 11, 12, 14**) use a 70% bias toward generating `Fun` types. This forces the generator into recursive `Lam` and `App` structures, which is the primary driver for the high `unique_subterms_proportions_average` (0.95 in the best program).
*   **Tiered Generation Priority**: The current best program implements a clear hierarchy: 1) Match `Var` from context, 2) Match `App` from context callables, 3) Inject complex Redex-Chains, 4) Standard Lambda/App generation. This tiered approach ensures that the most "valuable" metrics (vars and redexes) are attempted first before falling back to simpler structures.
*   **Safety Fallbacks for Termination**: To maintain a 1.00 `good_ratio`, **Generation 14** includes explicit base cases for when `budget <= 1`, returning simple literals or an "unused" identity lambda. This prevents the generator from returning `None` or an invalid structure when the budget is exhausted.

## Performance Analysis

*   **The 12.38 Ceiling**: The progression from **Generation 12** (12.37) to **Generation 14** (12.38) shows that marginal gains are now coming from fine-tuning the balance between `applied_lambdas` and `used_vars`. The best program successfully increased the variable usage proportion to 0.40 without sacrificing the 0.62 redex proportion.
*   **Correlation between Context Re-use and Score**: There is a clear trend where programs that prioritize `arg_ty` from the context (**Generation 14**) score higher than those that generate random `arg_ty` (**Generation 10**). This is because context re-use improves two metrics simultaneously: `used_vars` and `good_ratio`.
*   **Stability of Structural Diversity**: Across all successful programs (**Generations 11-14**), the `unique_subterms_proportions_average` has stabilized between 0.91 and 0.95. This suggests that the current recursive strategies are highly effective at generating diverse term trees, and further optimization should focus on specific node types (Redexes/Vars) rather than general diversity.
*   **Complexity vs. Validity Trade-off**: **Generation 13**'s drop to 9.08 demonstrates that there is a "complexity wall." Pushing redex density too aggressively without sophisticated budget management and context-aware type matching results in a significant performance penalty due to validity failures.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Implement Deep Currying for Callable Lookups**: Extend the "Medium Priority" callable lookup to search for variables that return the `target_ty` after multiple applications (e.g., to get `C`, look for `A -> B -> C`). This will generate nested `App(App(Var, arg1), arg2)` structures, which increases `tm_sizes_average` and `used_vars_proportions_average` by utilizing existing context variables as arguments for multi-parameter functions.

2. **Introduce "Redex-Chain" Depth Scaling**: The current "Redex-Chain" is fixed at two binders (`v1`, `v2`). Implement a version that dynamically scales the chain length (2 to 4 binders) based on the remaining budget (e.g., if `budget > 60`). This will push the `applied_lambdas_proportions_average` beyond the current 0.62 ceiling by creating denser clusters of redexes in a single branch.

3. **Type-Directed Variable Shadowing**: Occasionally (10-15% chance) reuse a variable name already present in the context when generating a `Lam`. This "shadowing" forces the generator to create more complex term structures and increases `unique_subterms_proportions_average` by ensuring that identical-looking subtrees are actually distinct due to their binding depth, while also testing the robustness of the context management.

4. **Biased Argument Selection for Redexes**: In the "Explicit Redex" and "Redex-Chain" blocks, instead of generating a random `arg_ty`, force the `arg_ty` to be a `Fun` type 50% of the time. This encourages "Higher-Order Redexes" where the argument being passed into a lambda is itself a lambda or an application, significantly increasing structural complexity and the `applied_lambdas` metric.

5. **Dynamic Budget Reallocation for High-Value Nodes**: Replace the static `budget // 3` and `budget // 5` splits with a "greedy" allocation that gives 70-80% of the remaining budget to the "operator" side of an `App` if a redex is being injected. This ensures that the lambda portion of the redex has enough budget to be a complex, multi-variable term, while the "argument" side remains a compact, context-using `Var` or literal.
