# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

*   **Proactive Type-Matching for Applications**: The current best program (Gen 33, Score: 10.88) avoids the "random generation" trap by explicitly defining an `arg_type` and `ret_type` before constructing an `App` term. It then ensures the function part of the application is either a `Lam` or a `Var` that matches that specific signature. This led to an `applied_lambdas_proportions_average` of 0.18, whereas programs like Gen 45 failed entirely (Score 0.0) because they generated `App` terms with mismatched types.
*   **Context-Aware Variable Injection with Probability Weighting**: Passing a `bound_vars` list of `(name, type)` tuples through recursive calls is the most reliable method for generating valid `Var` terms. The best program (Gen 33) uses a 35% probability to select from this list, achieving a `used_vars_proportions_average` of 0.18. This is significantly more effective than Gen 41 (Score: 10.17), which used more aggressive fallback logic that limited term complexity.
*   **Recursive Depth-Limited Branching with Strict Decrement**: Successful programs (Gen 33, Gen 41) use a strict `depth - 1` decrement. Gen 33 uses this to balance between base-case literals and complex structures, reaching a `tm_sizes_average` of 4.34. In contrast, programs that lacked this discipline or had incomplete recursive branches (Gen 46, 47, 49) failed to execute or pass validation.
*   **Fresh Variable Generation with F-Strings**: Gen 33 utilizes `f"x{rng.randint(0, 100)}"` for lambda binders. This strategy, combined with the recursive structure, resulted in a `unique_subterms_proportions_average` of 0.39, preventing the structural repetition that limits the scores of simpler generators.

## Ineffective Approaches

*   **Type-Agnostic Application Construction**: Gen 45 (Score: 0.0) failed because it attempted to build `App` terms without ensuring the function's input type matched the argument's type. This highlights that in STLC, "random" generation must be constrained by the type system to pass validation.
*   **Undefined Function References and "EVOLVE-BLOCK" Errors**: Multiple programs (Gen 46, 47, 49) failed with a score of 0.0 because they referenced `generate_sample` within their own definitions without actually defining the logic, or left the implementation incomplete. This indicates that the evaluation environment requires a fully self-contained, executable function.
*   **Literal-Only Defaults (The "Safe" Trap)**: Programs like Gen 40 (Score: 3.34) and Gen 43 (Score: 1.83) implemented only base cases (Bool, Int, String). While this ensures a valid `good_ratio`, it results in zero variable usage and zero applications, leading to significantly lower scores than programs that attempt complex structures like Gen 33.
*   **Hardcoded Type Assumptions**: Gen 38 (Score: 0.0) attempted to wrap all terms in a function accepting an `Int`. This ignored the actual context requirements of the inner terms, leading to type-checking failures and validation rejection.

## Implementation Insights

*   **Co-generation of Type and Term**: The most effective programs (Gen 33, Gen 41) return a `(type, term)` tuple. This allows the generator to maintain an "on-the-fly" symbol table, ensuring that every `Var` and `App` is type-correct at the moment of creation. This is the primary driver behind Gen 33's 0.99 `good_ratio`.
*   **Strategic Probability Weighting**: Gen 33 balances its output by using specific probabilities: 50% for base cases at the top level, 35% for variable usage if available, and a 50/50 split between creating new lambdas or applications. This distribution is key to achieving a `tm_sizes_average` of 4.34, the highest among all evaluated programs.
*   **Structural Complexity vs. Correctness**: Gen 33 demonstrates that a slight dip in `good_ratio` (0.99 vs 1.00 in literal-only versions) is a favorable trade-off for a massive increase in term size and variable utilization. The scoring algorithm rewards the presence of `App` and `Var` terms more heavily than perfect literal-only correctness.

## Performance Analysis

*   **The 10.80+ Performance Ceiling**: Gen 33 (Score: 10.88) remains the benchmark. It maximized three metrics simultaneously: `tm_sizes_average` (4.34), `used_vars_proportions` (0.18), and `applied_lambdas_proportions` (0.18). 
*   **Complexity Correlation**: There is a direct correlation between `tm_sizes_average` and the final score among programs that pass validation. Gen 41 (Size 1.15) scored 10.17, while Gen 33 (Size 4.34) scored 10.88. Programs with Size 1.00 (Gen 40, 43) scored below 3.5.
*   **The Penalty of Incompleteness**: Programs that fail to implement the full AST (Gen 40, 43) or have syntax/reference errors (Gen 45, 46, 47, 49) receive scores of 0.0 or very low values. This confirms that the evaluation environment prioritizes a functional, fully-implemented recursive structure over ambitious but broken fragments.
*   **Type-Safety as a Binary Gate**: Programs that do not strictly enforce type-matching in `App` terms (Gen 45) receive a score of 0.0, regardless of how complex their logic is. Type-safety is a prerequisite for any score above zero.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Implement Strict Type-Directed Generation with a `target_type` Parameter**: The current best program generates arguments and function bodies without ensuring they match the required types, relying on luck or simple defaults. Modify `generate_sample` to accept an optional `target_type`; when generating an `App` term's argument or a `Lam` body, pass the specific required type to the recursive call. This will ensure the `good_ratio` remains near 1.0 even as structural complexity increases.

2. **Recursive Type Generation for Higher-Order Functions**: Currently, `arg_type` and `ret_type` are mostly limited to base types, capping `ty_sizes_average` at 1.34. Create a helper function `generate_type(rng, depth)` that can recursively produce `FunTy` structures. Using these complex types in `Lam` binders and `App` signatures will naturally increase both type and term complexity, pushing the score beyond the current ceiling.

3. **Type-Filtered Variable Selection**: The current 35% probability for `Var` terms picks any variable, often leading to type mismatches in nested contexts. Implement a filter that scans `bound_vars` for entries matching the `target_type`. If a match exists, prioritize selecting it; this "smart selection" will significantly boost `used_vars_proportions_average` and prevent the generator from falling back to literals when a valid variable is available.

4. **Dynamic Depth-Based Branch Weighting**: To push `tm_sizes_average` beyond 4.34, implement a weighting system where the probability of choosing `App` or `Lam` is high (e.g., 0.8) at shallow depths and decreases as recursion nears the limit. This forces the generator to build deeper, more nested structures early on, only settling into "safe" base cases (literals) when the depth limit is reached.

5. **Guaranteed Function Synthesis in Applications**: In the `App` branch, the current program often creates a `Lam` that might not return the correct `ret_type`. Refine this by explicitly generating the function part of an application as a `Lam` whose body is recursively called with the specific `ret_type` as its `target_type`. This ensures that every `App` constructed is structurally valid and type-consistent, maximizing the `applied_lambdas_proportions_average`.
