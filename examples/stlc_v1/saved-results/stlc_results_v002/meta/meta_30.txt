# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

*   **Type-Consistent Application Synthesis**: The current best program (Gen 33, Score: 10.88) significantly improved performance by ensuring that `App` terms are constructed with matching types. Unlike Gen 26, which failed to ensure the left-hand side was a function, Gen 33 explicitly generates a `func_type` and then constructs a `Lam` or `Var` that satisfies that specific `arg_type`. This led to an `applied_lambdas_proportions_average` of 0.18, a massive leap from the 0.00-0.06 seen in earlier versions.
*   **Context-Aware Variable Injection**: Building on the success of Gen 28, Gen 33 uses a `bound_vars` list containing `(name, type)` tuples. By using `rng.choice(bound_vars)` with a 35% probability, it achieved a `used_vars_proportions_average` of 0.18. This confirms that passing the context through recursive calls is the most reliable way to generate valid `Var` terms.
*   **Recursive Depth-Limited Branching**: The most successful programs (Gen 30, Gen 33) use a strict `depth - 1` decrement in recursive calls. Gen 33 specifically uses this to balance between literals (base cases) and complex structures (`Lam`, `App`). This discipline allowed Gen 33 to reach a `tm_sizes_average` of 4.34, more than double the 2.12 of Gen 28, while maintaining a 0.99 `good_ratio`.
*   **Fresh Variable Generation with F-Strings**: Gen 33 uses `f"x{rng.randint(0, 100)}"` for lambda binders. This strategy, combined with the recursive structure, resulted in a `unique_subterms_proportions_average` of 0.39, the highest recorded, preventing the structural repetition that limited the scores of Gen 30 (0.27).

## Ineffective Approaches

*   **Isolated Code Blocks and Syntax Errors**: Generations 32 and 35 (Score: 0.0) failed because they included "EVOLVE-BLOCK" markers or logic outside of valid function definitions. This demonstrates that even sophisticated logic is worthless if the Python interpreter cannot parse the file, a recurring issue when attempting to transition from simple to complex generators.
*   **Logic Omission (Literal-Only Defaults)**: Generation 36 (Score: 3.49) and Generation 30 (Score: 10.26) suffered from incomplete logic. Gen 36 failed to implement `Lam` or `App` entirely, while Gen 30 was so biased toward base cases that it produced an average term size of only 1.24. This "safe" approach prevents errors but results in a low complexity score.
*   **Unchecked Function Application**: As seen in Gen 26 (Score 7.32) and referenced in previous insights, attempting to create `App` terms without verifying that the operator is a `FunTy` leads to a high rate of ill-typed terms, dragging down the `good_ratio` and the overall score.

## Implementation Insights

*   **The "Function-First" Application Strategy**: The current best program (Gen 33) is effective because it "pre-calculates" the required types for an application. It chooses an `arg_type` and `ret_type` first, then forces the creation of a function term that fits that signature. This is more successful than generating two random terms and hoping they are compatible.
*   **Co-generation of Type and Term**: Programs that return a `(type, term)` tuple (Gen 33, Gen 30, Gen 28) consistently outperform those that try to generate terms in isolation. This allows the generator to maintain an "on-the-fly" symbol table, ensuring that every `Var` and `App` is type-correct at the moment of creation.
*   **Structural Complexity vs. Correctness**: Gen 33 demonstrates that a slight dip in `good_ratio` (0.99 vs 1.00 in Gen 30) is a favorable trade-off for a 350% increase in term size (4.34 vs 1.24). The scoring algorithm rewards the presence of `App` and `Var` terms more heavily than perfect literal-only correctness.

## Performance Analysis

*   **The 10.80+ Breakthrough**: Gen 33 (Score 10.88) represents the new performance ceiling. It achieved this by maximizing three metrics simultaneously: `tm_sizes_average` (4.34), `used_vars_proportions` (0.18), and `applied_lambdas_proportions` (0.18). Previous high-scorers like Gen 30 (10.26) were limited by zero applications and minimal term sizes.
*   **Complexity Correlation**: There is a direct correlation between `tm_sizes_average` and the final score among "Correct" programs.
    *   Gen 36: Size 1.00 -> Score 3.49
    *   Gen 30: Size 1.24 -> Score 10.26
    *   Gen 28: Size 2.12 -> Score 10.55

*   **The Penalty of Incompleteness**: Programs that fail to implement the full AST (Gen 36) or have syntax errors (Gen 32, 35) receive scores between 0.0 and 3.5, which is significantly lower than even the most basic literal generator (10.26). This confirms that the evaluation environment prioritizes a functional, albeit simple, recursive structure over ambitious but broken implementations.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Implement a Recursive Type Generator for Higher-Order Functions**: The current best program (Gen 33) mostly uses base types for `arg_type` and `ret_type`. By creating a `generate_type(rng, depth)` helper that can recursively produce `FunTy` (e.g., `(Int -> Bool) -> String`), you can increase `ty_sizes_average` and enable the generation of higher-order functions, which are necessary to reach more complex `App` structures and higher scores.

2. **Refine Variable Selection via Type-Matching**: Instead of using `rng.choice(bound_vars)` and potentially returning a type that doesn't fit the current branch's needs, modify `generate_sample` to accept an optional `target_type`. When selecting a variable, filter `bound_vars` for those matching `target_type`; this will significantly increase the density of valid, used variables and improve the `good_ratio` when generating complex applications.

3. **Dynamic Weighting for Structural Growth**: To push `tm_sizes_average` beyond 4.34, implement a "warm-up" phase where the probability of choosing `Lam` or `App` is significantly higher (e.g., 80-90%) when `depth` is high and `bound_vars` is small. This ensures the generator builds a substantial "context" of variables early in the recursion, preventing it from defaulting to simple literals too quickly and resulting in larger, more interesting terms.

4. **Ensure Type-Correctness in Application Arguments**: In Gen 33, the `arg_term` is generated without ensuring its type matches the `arg_type` of the function. Modify the recursive call for `arg_term` to specifically request a term of `arg_type`. This "Type-Driven Synthesis" will eliminate the current "guess-and-check" nature of applications, maximizing the `applied_lambdas_proportions_average` by ensuring every `App` is valid.

5. **Introduce Structured Variable Shadowing**: Improve `unique_subterms_proportions_average` by replacing the random `randint(0, 100)` naming with a scoped approach like `f"x{len(bound_vars)}"`. This makes variable names predictable and allows for intentional shadowing (reusing a name from an outer scope), which tests the robustness of the term representation while keeping the generated code more compact and structurally diverse.
