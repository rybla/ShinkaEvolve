# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

*   **Context-Aware Variable Tracking**: The most successful programs (Generation 30 and the Current Best Program) utilize a `context` list passed through recursive calls. This allows the generator to track bound variables, enabling the creation of `VarTm` nodes. The Current Best Program achieved the highest combined score (10.31) by combining this context with a 30% probability of variable selection.
*   **Recursive Depth Management**: Programs that successfully generated valid terms (Generations 30, 31, 33) used a `depth` parameter to control recursion. The Current Best Program specifically uses `depth` to toggle between terminal literals and recursive function generation (`4 if depth > 0 else 3`), ensuring termination while allowing for nested structures.
*   **Identity-Like Abstraction Wrapping**: A consistent pattern in high-performing programs (good_ratio 1.00) is wrapping a base literal or a recursive term in a `Lam` constructor. This ensures type consistency by matching the `Lam` body's type with the return type of the `Fun` constructor.
*   **Deep Embedding Alignment**: The Current Best Program strictly adheres to the tuple-based deep embedding (`('Lam', name, type, body)`), which is critical for passing validation. Programs that deviated or had incomplete logic (Generations 34 and 35) resulted in a 0.0 score.

## Ineffective Approaches

*   **Static Depth Parameters**: Generation 31 failed to decrement the `depth` parameter during recursive calls. While it avoided infinite recursion due to a random distribution favoring literals, this logic is fragile and limits the generator's ability to reliably produce complex, deep structures.
*   **Missing `AppTm` Logic**: Across all successful generations (30, 31, 33, and Best), there is a total absence of `AppTm` (Application) generation. This results in `applied_lambdas_proportions_average` remaining at 0.00, significantly capping the potential structural complexity and score.
*   **Incomplete Evolution Blocks**: Generations 34 and 35 failed entirely (score 0.0) because they attempted more complex logic (like updating context) but left the implementation unfinished or syntactically broken (e.g., orphaned `else` blocks).
*   **Hardcoded Type Assumptions**: Many programs (including the Best Program) hardcode the parameter type of lambdas to `("Int",)`. While this ensures validity, it limits the variety of types and prevents the generation of higher-order functions (functions that take other functions as arguments).

## Implementation Insights

*   **Probability-Driven Branching**: The Current Best Program uses `rng.randrange` to decide between generating a literal or a function. This simple branching, combined with a 30% chance to pull from the `context`, resulted in a `tm_sizes_average` of 1.38, the highest among the successful programs.
*   **Variable Shadowing and Context**: While Generation 30 and the Best Program use a context, they often produce "identity-like" functions where the lambda variable `x` is introduced but not necessarily used (unless the 30% random check triggers). This explains why `used_vars_proportions_average` remains 0.00 in the metrics—the variables are being bound but not effectively referenced in a way that the evaluator counts as "utilization."
*   **Tuple-Based Type Construction**: The successful programs correctly map the Python type aliases to tuple structures (e.g., `("Fun", ("Int",), ty)`). The Current Best Program demonstrates that keeping the type structure simple (Int-to-X) is a reliable way to maintain a 1.00 `good_ratio`.

## Performance Analysis

*   **Complexity vs. Validity Trade-off**: There is a clear plateau in performance. Generations 30, 31, and 33 all hovered around a 10.28 score with an average term size of ~1.3. The Current Best Program achieved a slight lead (10.31) by marginally increasing the average term/type size to 1.38.
*   **The "Zero Metric" Barrier**: Despite being "Correct," all programs currently fail to generate any `AppTm` (0.00 applied lambdas) and fail to effectively utilize variables (0.00 used vars). This indicates that while the programs are syntactically correct, they are not yet exercising the full semantics of the Simply-Typed Lambda Calculus.
*   **Impact of Context**: Programs that implemented a context (Generation 30 and Best) did not necessarily see an immediate jump in `used_vars_proportions_average`, but they achieved higher `unique_subterms_proportions_average` (0.15) compared to those that did not, suggesting that variable names add to the structural variety of the generated code.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Implement `AppTm` (Application) Generation**: To break the "Zero Metric" barrier for applied lambdas, introduce a new branch in the `generate_sample` function that generates an `AppTm`. This requires generating a function term (e.g., a `Lam`) and a matching argument term of the correct input type. Start by hardcoding the application to simple `Int -> Int` functions to ensure type validity while increasing structural complexity.

2. **Synchronize Variable Names with Context**: The current `used_vars_proportions_average` is 0.00 because the generator often introduces a variable (e.g., `"x"`) but then pulls a different, potentially non-existent or shadowed variable name from the `context`. Update the `Lam` generation to append the specific `name` it just created to the `context` passed to its body's recursive call, ensuring that `Var` nodes can actually reference the current scope's parameters.

3. **Diversify Lambda Parameter Types**: Move beyond the hardcoded `("Int",)` parameter type by randomly selecting a base type (`Bool`, `Int`, or `String`) for the lambda's input. This will increase `ty_sizes_average` and `unique_subterms_proportions_average` while maintaining a high `good_ratio`, as long as the `Var` nodes and `AppTm` logic respect these dynamically chosen types.

4. **Refine Depth-Based Termination Logic**: Improve the `depth` management by ensuring it decrements in every recursive call and using it to strictly force a terminal literal (i.e., `i = rng.randrange(0, 3)`) when `depth == 0`. This prevents the "fragile logic" seen in previous generations and allows for a higher initial depth (e.g., 5-10) to produce much larger and more complex terms without risking infinite recursion.

5. **Introduce Type-Safe Variable Selection**: Instead of a simple list of names, modify the `context` to store tuples of `(name, type)`. When generating a `VarTm`, the generator should filter the context for names that match the *expected* return type of the current branch. This targeted selection will significantly increase the success rate of generating deep, valid terms that utilize variables correctly.
