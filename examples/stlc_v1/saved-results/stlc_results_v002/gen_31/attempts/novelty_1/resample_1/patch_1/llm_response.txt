The current implementation of the "Dynamic Redex-Chain" is slightly flawed in its construction: it builds a nested lambda `(λv1. λv2. body)` and then applies it to arguments in a way that doesn't correctly form a standard left-associated application chain `((f arg1) arg2)`. Specifically, the current loop `for i in range(n): res = ("App", res, arg_tm)` creates a right-associated structure or applies the entire lambda block to each argument sequentially in a non-standard way for redexes.

To maximize `applied_lambdas_proportions_average` and `tm_sizes_average`, we will:
1.  **Fix the Redex-Chain**: Correctly nest the applications so that `(λv1...vn. body)` is applied to `n` arguments in a standard curried fashion: `(...((Lam_block arg1) arg2) ... argn)`.
2.  **Increase Context Sensitivity**: When generating arguments for the redex chain, we will prioritize picking variables from the context that match the required `arg_types` to boost `used_vars_proportions_average`.
3.  **Type Generation Bias**: Adjust `gen_type` to produce slightly more balanced trees, which provides better variety for the `App` nodes to target.
