# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

*   **Explicit Redex Injection**: The current best program (Generation 9, score 12.34) introduced a specific "Explicit Redex" block that generates an `App` of a `Lam` even when not strictly required by the type. This strategy, combined with a 30% probability trigger, directly boosted the `applied_lambdas_proportions_average` to 0.61, the highest recorded.
*   **Context-Driven Application (Callable Lookup)**: Successful programs (Generations 7 and 9) prioritize searching the context for variables of type `Fun` that return the `target_ty`. Generation 7 achieved a score of 12.17 by using this "targeted search," which ensures that applications are meaningful and utilize existing variables rather than just generating new sub-trees.
*   **Weighted Type Generation with High Function Bias**: Consistently high-performing programs (Generations 6, 7, and 9) use a 70% bias toward generating `Fun` types. This creates a "top-heavy" type structure that forces the term generator to use `Lam` and `App` nodes, leading to high unique subterm proportions (0.94 in Generation 9).
*   **Proportional Budget Splitting**: The most stable and high-scoring programs (Generations 6 and 9) use a 50/40 or 60/40 budget split for `App` nodes. This prevents lopsided trees and ensures that both the function and the argument branches have enough "fuel" to generate complex terms, maintaining a 1.00 `good_ratio`.

## Ineffective Approaches

*   **Undefined Module References**: Generation 5 failed completely (score: nan) due to a `NameError` from referencing `List` without importing it from `typing`. This highlights that even sophisticated logic (budget splitting, type-matching) is useless without basic import validation.
*   **Over-Engineering with Memoization**: Generation 8 (score 0.0) attempted to implement a local memoization cache and "redex boosting." This complexity likely led to type-safety fallbacks or recursion depth issues that violated STLC requirements, proving that structural integrity is more important than algorithmic complexity.
*   **Unconstrained Random Argument Generation**: Earlier failed attempts (Generation 1) generated random argument types for `App` nodes without checking if those types could be satisfied within the remaining budget, leading to invalid terms or termination failures.
*   **Literal Bias**: Generation 0 (score 10.28) relied on hardcoded literals. While valid, this resulted in a very low average term size (1.33) and failed to utilize the variable context, resulting in the lowest scores among valid programs.

## Implementation Insights

*   **Dynamic Variable Naming**: The current best program (Generation 9) uses `f"v{len(ctx)}"` to generate unique variable names. This allows the generator to track the depth of the context and ensures that `Var` nodes always point to valid, type-matched binders, contributing to a `used_vars_proportions_average` of 0.39.
*   **Type-Safety Fallbacks**: Generation 9 includes specific fallback logic for literals and a "safety" `Lam` for unexpected `Fun` types. This ensures that even if the budget is exhausted, the function returns a valid `Tm` that matches the `target_ty`, maintaining the 1.00 `good_ratio`.
*   **Contextual Variable Re-use**: To boost variable usage, Generation 9 attempts to pick an `arg_ty` for an `App` node from the existing context (50% chance) rather than generating a new random type. This links different parts of the term tree together through shared variables.
*   **Budget-Triggered Termination**: The use of a `budget` parameter that decreases with each recursive call (e.g., `budget - 1` for `Lam`, `budget // 2` for redexes) is the primary mechanism for controlling term size while allowing for deep trees (average size 11.94).

Generation 6 (0.50 proportion) scored 12.12, while Generation 9 (0.61 proportion) reached 12.34. Explicitly forcing `App(Lam(...), ...)` structures is the most effective way to increase this metric.
*   **Complexity vs. Validity**: Generation 9 achieved the highest score (12.34) by balancing a high budget (85) with strict type-matching. It outperformed Generation 7 (12.17) primarily by increasing the `used_vars_proportions_average` from 0.31 to 0.39 through more aggressive context exploitation.
*   **Unique Subterm Saturation**: Most high-performing programs (Generations 7 and 9) have hit a "ceiling" in `unique_subterms_proportions_average` at 0.94. This suggests that the recursive generation of random types and terms naturally produces high structural diversity.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Implement Deep Currying for Callable Lookups**: The current "callable lookup" only finds variables that return the `target_ty` directly. Extend this logic to search the context for variables whose return type is a function that *eventually* returns the `target_ty` (e.g., to get `C`, look for `A -> B -> C`). This will generate nested `App` nodes and significantly increase both `tm_sizes_average` and `applied_lambdas_proportions_average` by chaining applications.

2. **Introduce "Redex-Chain" Generation**: Building on the success of the "Explicit Redex" block (which currently generates a single `App(Lam, arg)`), implement a version that generates a chain of redexes (e.g., `App(App(Lam, Lam), arg, arg)`). By increasing the probability of these structures when the budget is high (>40), you can push the `applied_lambdas_proportions_average` beyond the current 0.61 ceiling.

3. **Context-Inhabited Argument Selection**: Instead of generating a random `arg_ty` for an `App` node, prioritize selecting a type that is already present in the context. If the context contains a variable of type `T`, use `T` as the `arg_ty` for the new `App` node; this creates a "virtuous cycle" where new applications are guaranteed to have a variable ready to be used as an argument, boosting `used_vars_proportions_average`.

4. **Dynamic Budget Reallocation for High-Value Nodes**: Currently, budget splitting is static (e.g., 50/40). Implement a "greedy" budget allocation where, if a "callable lookup" or "redex injection" is triggered, it receives a larger share of the remaining budget (e.g., 80%) to ensure these complex structures are fully realized rather than truncated by the fallback literal logic.

5. **Type-Directed Variable Shadowing**: To increase `unique_subterms_proportions_average` and test the robustness of the context, occasionally (10% chance) reuse a variable name already in the context when generating a `Lam`. This "shadowing" forces the generator to handle overlapping scopes and creates more complex term structures that differ from the standard `v0, v1, v2` linear progression.
