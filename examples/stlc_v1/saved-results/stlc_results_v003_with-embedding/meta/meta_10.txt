# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

*   **Dynamic Redex Injection Probability**: The current best program (Generation 7, score 12.21) introduced a scaling `redex_prob = 0.2 + (budget / 200.0)`. This ensures that as the budget increases, the likelihood of forcing a `(App (Lam ...) Arg)` structure increases, directly optimizing the `applied_lambdas_proportions_average` (0.39) while maintaining a 1.00 `good_ratio`.
*   **Recency-Biased Variable Selection with Context Windowing**: Generations 7, 8, and 9 all utilized a "recency bias" to improve variable usage. Generation 7 specifically targeted the last 5 entries (`ctx[-5:]`) for selection. This approach raised the `used_vars_proportions_average` to 0.19, a significant improvement over the 0.10 seen in unbiased models like Generation 4.
*   **Type-Directed Fallback for Function Types**: Unlike Generation 5 (score 1.24), which failed by producing literals for function types when the budget was exhausted, the successful programs (Generations 6-9) implement a recursive fallback. If a `FunTy` is required at `budget <= 1`, they force a `Lam` construction, ensuring the term remains well-typed and boosting the `good_ratio` to 1.00.
*   **Strategic Weighting of Term Constructors**: The best program (Generation 7) uses a weighted selection system (`lam: 10, var: 15, app: 25, lit: 5`) that heavily favors `App` nodes. This weighting, combined with a high initial budget (100), resulted in the highest average term size (16.85) and the highest overall score.

## Ineffective Approaches

*   **Literal Fallbacks for Complex Types**: Generation 5 demonstrated that returning a literal when a function type is expected results in a catastrophic drop in `good_ratio` (0.05). This "lazy" base-case logic prevents the generation of valid, deep structures.
*   **Aggressive Budget Halving**: Generation 6 (score 11.98) used a strict budget-halving logic in applications. While it maintained validity, its average term size (13.42) was lower than Generation 7 (16.85), which used a more flexible `rng.randint(1, budget - 1)` split, allowing for more asymmetric and thus potentially deeper/more complex trees.
*   **Uniform Context Sampling**: Previous insights and Generation 4 showed that picking any valid variable from the entire context leads to lower usage scores (0.10). Variables defined early in a deep recursion are often "shadowed" or logically distant, making them less likely to be integrated into the current subterm compared to the recency-bias approach.

## Implementation Insights

*   **Context-Aware Argument Synthesis**: Generation 9 (score 12.00) attempted to pick argument types from existing variables in the context. While this is a sophisticated way to increase variable usage, the simpler "Redex Injection" and "Recency Bias" in Generation 7 (score 12.21) proved slightly more effective for the overall score by prioritizing structural complexity.
*   **Unique Identifier Generation**: All high-performing programs (Generations 6-9) use a combination of context length and random integers for variable names (e.g., `f"x{len(ctx)}_{rng.randint(0, 1000)}"`). This technique is responsible for the very high `unique_subterms_proportions_average` (0.97 in Gen 7), preventing the generator from repeating identical sub-structures.
*   **Intermediate Type Generation for Applications**: To create an `App` node, the generator must synthesize a domain type for the function that doesn't exist in the target type. The best programs use `gen_type(rng.randint(1, 4))` to create small, manageable intermediate types, ensuring the resulting `App` is well-typed without exploding the complexity of the type itself.

## Performance Analysis

*   **The "Redex" Correlation**: There is a direct correlation between explicit redex injection and the final score. Programs that "forced" lambdas into the left side of applications (Generations 6, 7, 8, and 9) all scored between 11.91 and 12.21. Programs without this (like Gen 0) stayed near 10.29.
*   **Term Size vs. Validity**: Generation 7 achieved the highest `tm_sizes_average` (16.85) among the successful programs. This suggests that the current scoring metric rewards larger terms as long as the `good_ratio` remains at 1.00. The jump from Generation 6's 13.42 to Generation 7's 16.85 was a key driver in reaching the 12.21 score.
*   **Variable Usage Ceiling**: Despite various strategies (recency bias, context-aware argument selection), `used_vars_proportions_average` remains the most difficult metric to move, peaking at 0.19 in Generation 7. This suggests that the "base case" (where variables are actually used) is still frequently bypassed by literals or that the budget is often exhausted before variables can be integrated.
*   **Consistency of Top-Tier Programs**: Generations 6 through 9 show very stable performance (scores 11.91 to 12.21), indicating that the combination of **Budget-based Recursion**, **Redex Injection**, and **Type-Directed Synthesis** is the optimal architectural pattern for this task.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Implement a "Variable-Hungry" Base Case**: To break the 0.19 ceiling on `used_vars_proportions_average`, modify the `budget <= 1` fallback to prioritize `Var` selection with a high probability (e.g., 85-90%) whenever `valid_vars` is non-empty. Currently, literals are often chosen by default for base types, but forcing variable usage at the leaves of the tree will ensure that the variables bound in the many `Lam` nodes created by the redex-injection strategy are actually consumed.

2. **Context-Aware Argument Type Synthesis**: Instead of generating a completely random `arg_ty` for `App` nodes using `gen_type(1, 4)`, select the type of an existing variable from the `ctx` with a 50% probability. This creates a "closed-loop" system where the `App` node is specifically designed to consume a variable already in scope, directly increasing the likelihood that the `a_tm` (argument term) will be a `Var` node.

3. **Asymmetric Budget Allocation for Higher-Order Functions**: In `App` nodes, when the target type `ty` is a `FunTy`, bias the budget split (e.g., 70/30) toward the function side (`f_tm`). This encourages the generation of complex, nested function transformations and deeper `Lam` structures, which provides more opportunities for both redex injection and variable binding, potentially increasing both the `tm_sizes_average` and `applied_lambdas_proportions_average`.

4. **Global Unique Identifier Counter**: Replace the `rng.randint(0, 1000)` naming scheme with a global incrementing counter to ensure absolute uniqueness of variable names across the entire term. While the current `unique_subterms_proportions_average` is high (0.97), absolute uniqueness prevents any possibility of variable shadowing, ensuring that every variable in the `ctx` remains a valid candidate for selection and maximizing the potential for `used_vars_proportions_average`.

5. **Dynamic Weighting based on Depth**: Introduce a depth tracking parameter and shift the `weights` for `choices` as the tree grows deeper. By increasing the weight of `App` and `Lam` at shallow depths and increasing the weight of `Var` and `Lit` as the budget decreases or depth increases, you can create "top-heavy" trees that are structurally complex but guaranteed to terminate cleanly, further pushing the `tm_sizes_average` without risking the `good_ratio`.
