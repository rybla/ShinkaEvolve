# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

*   **Power-Law Recency Bias for Variable Selection**: The current best program (**Generation 10**, score 12.37) significantly improved variable usage by applying a power-law distribution (`(i + 1)**2`) to the context. This approach, combined with context-aware argument selection, pushed the `used_vars_proportions_average` to **0.27**, a substantial increase over the 0.19 achieved by the simple windowing in Generation 7.
*   **Dynamic Redex Injection with Budget Scaling**: High-performing programs (Generations 10, 12, and 13) all utilize a "Redex Injection" strategy where `App` nodes are explicitly constructed as `(App (Lam ...) Arg)`. The best program uses a scaling probability `0.3 + (budget / 150.0)`, which successfully maximized the `applied_lambdas_proportions_average` to **0.49**.
*   **Context-Aware Argument Type Synthesis**: A recurring pattern in the most successful programs (Generations 10-15) is sampling `arg_ty` from the existing typing context rather than generating a random type. This ensures that when an `App` is created, there is a high probability that a variable already exists to satisfy the argument, directly contributing to the 1.00 `good_ratio` and higher variable usage.
*   **Weighted Constructor Selection with Function Bias**: The best program (Generation 10) uses a specific weight distribution (`lam: 15, var: 20, app: 35, lit: 5`) that heavily favors applications. By prioritizing `App` and `Lam` over literals, it maintains a high average term size (16.17) and structural complexity.

## Ineffective Approaches

*   **Uniform Variable Selection**: As seen in earlier iterations and noted in previous insights, picking variables uniformly from the context leads to low usage scores (approx. 0.10). The transition to recency-biased and power-law selection in **Generation 10** proved that local variables are much more likely to be integrated into subterms effectively.
*   **Static Redex Probabilities**: Programs that used a fixed, low probability for redex generation failed to reach the ~0.50 `applied_lambdas` threshold. The budget-scaled probability is necessary because it allows the generator to "spend" its complexity on redexes when the tree is deep, while tapering off as the budget vanishes to ensure validity.
*   **Literal Fallbacks for Function Types**: As demonstrated by **Generation 5** (score 1.24), returning a literal when a `FunTy` is expected causes a catastrophic drop in validity. All successful programs (Generations 10-15) now use a recursive fallback that forces a `Lam` construction even at `budget <= 1`.

## Implementation Insights

*   **Strategic Redex Synthesis**: The current best program (**Generation 10**) implements redex injection by manually constructing a `Lam` inside the function position of an `App`. This bypasses the standard recursive search for a function and guarantees an applied lambda, which is the primary driver for the 0.49 redex density.
*   **Context Sampling for Type Safety**: Programs like **Generation 11 (context_aware_redex_weaver)** and **Generation 12** explicitly pick argument types from `rng.choice(ctx)[1]`. This implementation detail ensures that the generated `App` nodes are not just structurally complex but are also "solvable" using existing variables, maintaining the 1.00 `good_ratio`.
*   **Unique Identifier Management**: To maintain a high `unique_subterms_proportions_average` (0.96 in Gen 10), successful programs combine the current context length with a random integer (e.g., `f"x{len(ctx)}_{rng.randint(0, 1000)}"`). This prevents the generator from producing identical variable names in different branches, which would otherwise collapse the uniqueness score.

## Performance Analysis

*   **The 12.0+ Score Ceiling**: There is a clear performance plateau between 12.04 and 12.37 across Generations 10 through 15. This suggests that the combination of **Power-Law Variable Selection**, **Redex Injection**, and **Context-Aware Type Synthesis** is the near-optimal configuration for this metric suite.
*   **Variable Usage vs. Redex Density**: **Generation 10** achieved the highest combined score (12.37) by balancing `used_vars_proportions` (0.27) and `applied_lambdas_proportions` (0.49). While other programs like **Generation 12** matched the redex density (0.50), they often had lower variable usage (0.21), indicating that the power-law bias is the specific differentiator for the top score.
*   **Stability of Validity**: All programs from Generation 10 onwards maintained a perfect 1.00 `good_ratio`. This confirms that type-directed synthesis, when paired with context-aware argument selection, is a robust method for generating valid terms even with highly aggressive structural injection strategies.
*   **Term Size Consistency**: Despite different "patch names" (e.g., `variable_hungry_synthesis` vs `context_aware_redex_synthesizer`), the average term sizes remained stable between 12.0 and 16.8. This indicates that the budget-based recursion (starting at 100) effectively regulates term growth regardless of the specific injection logic used.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Implement a "Variable-Hungry" Leaf Strategy**: To break the 0.27 ceiling on `used_vars_proportions_average`, modify the `budget <= 1` fallback to prioritize `Var` selection with a high probability (e.g., 85-90%) whenever `valid_vars` is non-empty. Currently, literals are often chosen by default for base types, but forcing variable usage at the leaves of the tree will ensure that the variables bound in the many `Lam` nodes created by the redex-injection strategy are actually consumed.

2. **Asymmetric Budget Allocation for Higher-Order Functions**: In `App` nodes, when the target type `ty` is a `FunTy`, bias the budget split (e.g., 70/30) toward the function side (`f_tm`). This encourages the generation of complex, nested function transformations and deeper `Lam` structures, which provides more opportunities for both redex injection and variable binding, potentially increasing both the `tm_sizes_average` and `applied_lambdas_proportions_average`.

3. **Global Unique Identifier Counter**: Replace the `rng.randint(0, 1000)` naming scheme with a global incrementing counter or a more robust `f"x{len(ctx)}_{depth}_{count}"` string to ensure absolute uniqueness of variable names across the entire term. While the current `unique_subterms_proportions_average` is high (0.96), absolute uniqueness prevents any possibility of variable shadowing, ensuring that every variable in the `ctx` remains a valid candidate for selection and maximizing the potential for `used_vars_proportions_average`.

4. **Dynamic Weighting based on Depth**: Introduce a depth tracking parameter and shift the `weights` for `choices` as the tree grows deeper. By increasing the weight of `App` and `Lam` at shallow depths and increasing the weight of `Var` and `Lit` as the budget decreases or depth increases, you can create "top-heavy" trees that are structurally complex but guaranteed to terminate cleanly, further pushing the `tm_sizes_average` without risking the `good_ratio`.

5. **Recursive Redex Injection**: Instead of a single-level `Lam` injection in `App` nodes, allow the redex-injection logic to occasionally (e.g., 10% of the time) inject a "double redex" `(App (Lam x (App (Lam y ...))))`. This would significantly boost the `applied_lambdas_proportions_average` beyond the current 0.49 by increasing the density of applications that are immediately reducible, while also providing more variables to the context for the power-law selection to utilize.
