# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

Based on the evaluation of the provided programs and the performance of the current best program (**Generation 24**, score **12.66**), the following optimization insights have been extracted:

### Successful Algorithmic Patterns

*   **Forced Variable Arguments in Redexes**: The most significant jump in variable utilization (from 0.38 to **0.46**) was achieved by **Generation 24** through a "Forced Variable Argument" rule. When injecting a redex `(App (Lam v body) arg)`, the generator checks the context for an existing variable matching the required type and selects it with a **90% probability**. This ensures that redexes serve as a primary driver for both `applied_lambdas` and `used_vars` metrics.
*   **Budget-Scaled Redex Probability**: Top-performing programs (**Generations 24, 28, and 29**) moved away from static probabilities to a dynamic formula: `redex_prob = 0.55 + (budget / 150.0)`. This ensures that at the start of generation (budget 100), the probability of creating a complex redex structure is nearly 100%, leading to a peak `applied_lambdas_proportions_average` of **0.64**.
*   **Quadratic Recency Bias with Context-Aware Type Selection**: Using `(i + 1)**2` to weight variable selection (seen in **Generations 24, 25, and 28**) has proven superior to linear or cubic biases. When combined with an **85% chance** to pick an `arg_ty` from the current context (as seen in **Generation 27**'s `TypeFrequencyMatch`), it ensures that the generated terms remain type-valid (1.00 `good_ratio`) while maximizing the reuse of locally bound variables.
*   **Asymmetric 70/30 Budget Splitting**: Every program scoring above 12.50 (**Generations 24-29**) utilized an asymmetric split (`split = int(budget * 0.7)`) for applications. By directing 70% of the budget to the function/body side, these programs achieved an average term size of **19.70**, significantly higher than those using uniform distribution.

### Ineffective Approaches

*   **Cubic Bias Over-Saturation**: While **Generation 23** attempted to increase variable reuse using a cubic bias `(i + 1)**3`, it resulted in a lower `good_ratio` (0.99). The evaluation suggests that extreme bias towards the most recent variables can lead to "leaf exhaustion," where the generator fails to find a valid termination path within the remaining budget for specific types.
*   **Fixed/Low Redex Probability**: Programs like **Generation 19** that used a fixed 55% redex chance consistently underperformed in structural complexity. Their `applied_lambdas` scores hovered around 0.55, compared to the 0.64 achieved by the budget-scaled approach in **Generation 24**.
*   **Random Type Generation for Arguments**: Programs that did not implement context-aware type selection (sampling `arg_ty` from the environment) struggled to maintain variable usage. Without this, the probability of a random type matching a variable in the context is low, keeping `used_vars` metrics below 0.30.

### Implementation Insights

*   **Synergistic Metric Optimization**: The current best program (**Generation 24**) succeeds by treating redex injection as a delivery mechanism for variables. By forcing the argument of an injected redex to be a context variable, it simultaneously boosts `applied_lambdas` and `used_vars`, creating a compounding effect on the total score.
*   **Global Uniqueness via Multi-Part Naming**: To maintain a high `unique_subterms` score (0.96), successful programs (**Generations 25, 28, and 29**) use a naming convention involving depth, a global counter, and a random integer: `f"{prefix}_{depth}_{var_counter}_{rng.randint(0, 100)}"`. This prevents structural collisions even when the same logic is generated in different branches.
*   **Weighted Constructor Selection**: **Generation 28** and **29** demonstrated that weighting `App` nodes (weight 60) higher than `Lam` (weight 25) or `Lit` (weight 10) is essential for driving term size and complexity without exceeding the 1.00 validity threshold.

### Performance Analysis

*   **The 12.6+ Performance Ceiling**: **Generation 24** (12.66) and **Generation 28** (12.63) represent the current peak. The common denominator is the combination of **Quadratic Recency Bias**, **Forced Variable Redexes**, and **Asymmetric Budgeting**.
*   **Stability of the 1.00 Validity Ratio**: Despite increasing `tm_sizes_average` to nearly 20.0, the `good_ratio` has remained at a perfect 1.00 across all top iterations. This indicates that the context-aware selection strategies are robust enough to handle significantly increased structural complexity.
*   **Correlation between Redexes and Variable Reuse**: Data from **Generation 24** shows a direct correlation between `applied_lambdas` (0.64) and `used_vars` (0.46). This confirms that the "Redex-First" strategy is the most effective way to increase variable utilization, as every injected redex provides a guaranteed opportunity to use a variable in the argument position.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Implement "Double-Redex" Injection**: To push the `applied_lambdas_proportions_average` beyond 0.64, modify the redex logic to occasionally (e.g., 20% of the time) inject a nested redex structure like `(App (Lam x (App (Lam y body) arg2)) arg1)`. This increases the density of immediate applications and provides two new variables to the context simultaneously, which synergizes with the quadratic recency bias to further boost variable usage.

2. **Introduce Depth-Dependent Constructor Weighting**: Shift the `weights` for constructor selection dynamically based on the current recursion depth or remaining budget. By increasing the weight of `App` and `Lam` at shallow depths (e.g., `app: 80` when `budget > 50`) and aggressively pivoting to `Var` at deeper levels, you can create "top-heavy" trees that maximize structural complexity and term size without hitting the recursion limit or failing the `good_ratio`.

3. **Context-Driven "Type-Matching" for Redexes**: Instead of generating a random `arg_ty` for redex injection, prioritize selecting a type that already exists multiple times in the current `ctx`. This ensures that the `a_tm` (the argument being passed to the injected lambda) has a much higher probability of being a `Var` rather than a `Lit`, directly targeting an increase in the `used_vars_proportions_average` which currently sits at 0.46.

4. **Asymmetric Budgeting for Function-Type Applications**: When generating a standard `App` (non-redex) where the result type `ty` is a `FunTy`, apply the `0.7` asymmetric budget split to the function side (`f_tm`). This encourages the creation of complex higher-order functions and deeper lambda chains, which provides more opportunities for the successful "must-generate" lambda fallback to trigger, increasing both `tm_sizes_average` and `applied_lambdas_proportions_average`.

5. **Refine Variable Selection with "Shadowing-Aware" Weights**: While the current quadratic bias `(i + 1)**2` is successful, it can be improved by adding a small bonus to variables that match the target type but are *not* the most recently added (e.g., `(i + 1)**2 + (10 if name.startswith("r") else 0)`). This encourages the generator to use variables created by redex injections (`r_` prefix) even if they are slightly further up the stack, maximizing the utility of the specific structural injections that define the current best-performing generation.
