# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

*   **Forced Variable Arguments in Redexes**: The current best program (**Generation 24**, score 12.66) introduced a "Forced Variable Argument" rule within its redex injection logic. When creating an `(App (Lam v body) arg)` structure, it checks the context for an existing variable matching `arg_ty` and uses it with a 90% probability. This specific change, combined with quadratic weighting, pushed the `used_vars_proportions_average` to a record **0.46**, a significant jump from the 0.38 seen in Generation 17.
*   **Budget-Scaled Redex Probability**: Unlike earlier versions that used a fixed 65% redex chance, the top-performing programs (**Generation 21** and **Generation 24**) implemented a dynamic probability: `redex_prob = 0.55 + (budget / 150.0)`. This ensures that as the generator starts with a large budget (100), the probability of injecting a redex is extremely high (~1.0), ensuring complex structures are established early before the budget dissipates. This led to the highest `applied_lambdas_proportions_average` of **0.64**.
*   **Quadratic and Cubic Recency Bias**: The transition from linear to non-linear weighting for variable selection has been a primary driver for validity and reuse. **Generation 22** (score 12.64) and **Generation 24** (score 12.66) utilized `(i + 1)**2`, while **Generation 23** (score 12.58) experimented with a cubic `(i + 1)**3` bias. The quadratic approach in Generation 24 appears to be the "sweet spot," balancing high variable usage (0.46) with perfect validity (1.00).
*   **Asymmetric 70/30 Budget Splitting**: Consistent across all programs scoring above 12.50 (Generations 19, 21, 22, 24) is the `split = int(budget * 0.7)` rule. By allocating 70% of the budget to the function body (the "left" side of an application or the body of a lambda), these programs achieve an average term size of **19.70**, nearly double the size of programs using uniform splitting.

## Ineffective Approaches

*   **Cubic Bias Over-Saturation**: While **Generation 23** achieved a high score (12.58), its use of a cubic bias `(i + 1)**3` resulted in a slightly lower `good_ratio` (0.99) compared to the perfect 1.00 of the quadratic versions. This suggests that extreme recency bias can occasionally lead to "leaf exhaustion" where the generator cannot find a valid path to terminate a branch within the remaining budget.
*   **Low-Probability Redex Injection**: Programs that relied on a lower redex injection probability (e.g., **Generation 19** at 0.55 vs **Generation 24**'s scaled approach) consistently saw lower `applied_lambdas` scores. Generation 19 achieved 0.55 in that metric, whereas the scaled probability in Generation 24 reached 0.64, directly accounting for the score difference (12.45 vs 12.66).
*   **Random Type Generation for Arguments**: As seen in earlier iterations and confirmed by the success of **Generation 24**, generating a random type for an application argument (rather than sampling the context) is inefficient. Programs that do not use the "85% Context-Aware Type Selection" fail to create the necessary conditions for variable reuse, keeping the `used_vars` metric below 0.30.

## Implementation Insights

*   **Synergy of Redex Injection and Variable Selection**: The current best program (**Generation 24**) demonstrates that redex injection is not just about the `applied_lambdas` metric; it is a delivery mechanism for variables. By forcing the argument of an injected redex to be a variable from the context (`arg_vars` check), it simultaneously optimizes two metrics, leading to its peak score of 12.66.
*   **Strategic Variable Naming for Uniqueness**: To maintain a high `unique_subterms_proportions_average` (0.96), the best programs use a multi-part naming convention: `f"{prefix}_{depth}_{var_counter}_{rng.randint(0, 100)}"`. This ensures that even if the same logic is generated in different branches, the variable names remain globally unique, preventing subterm collisions.
*   **Context-Matched Argument Selection**: **Generation 22** and **Generation 24** use a 85% probability to pick an `arg_ty` from the current context. This implementation detail ensures that the `App` nodes created are "resolvable" by existing variables, which is the primary reason these programs maintain a 1.00 `good_ratio` despite high term complexity.

## Performance Analysis

*   **The 12.6+ Score Plateau**: **Generation 24** (12.66) and **Generation 22** (12.64) have established a new performance ceiling. The common denominator is the combination of **Quadratic Recency Bias** and **Forced Redex Injection**.
*   **Term Size vs. Validity**: There is a clear trend where increasing `tm_sizes_average` (now at 19.70 in **Generation 24**) does not degrade the `good_ratio` (1.00), provided that the variable selection is sufficiently biased toward the local context. This disproves earlier assumptions that larger terms are inherently more prone to type errors.
*   **Metric Correlation**: The data from **Generation 24** shows a strong correlation between `applied_lambdas_proportions_average` (0.64) and `used_vars_proportions_average` (0.46). This confirms that the "Redex-First" strategy is the most effective way to increase variable utilization, as every injected redex provides a guaranteed opportunity to use a variable in the argument position.
*   **Consistency of Uniqueness**: Across all top programs (Generations 21-24), the uniqueness metric has stabilized at 0.96. This indicates that the current naming and literal generation strategies are optimal, and further score gains must come from structural density (lambdas and variables).

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Implement "Double-Redex" Injection**: To push the `applied_lambdas_proportions_average` beyond 0.64, modify the redex logic to occasionally (e.g., 20% of the time) inject a nested redex structure like `(App (Lam x (App (Lam y body) arg2)) arg1)`. This increases the density of immediate applications and provides two new variables to the context simultaneously, which synergizes with the quadratic recency bias to further boost variable usage.

2. **Introduce Depth-Dependent Constructor Weighting**: Shift the `weights` for constructor selection dynamically based on the current recursion depth or remaining budget. By increasing the weight of `App` and `Lam` at shallow depths (e.g., `app: 80` when `budget > 50`) and aggressively pivoting to `Var` at deeper levels, you can create "top-heavy" trees that maximize structural complexity and term size without hitting the recursion limit or failing the `good_ratio`.

3. **Context-Driven "Type-Matching" for Redexes**: Instead of generating a random `arg_ty` for redex injection, prioritize selecting a type that already exists multiple times in the current `ctx`. This ensures that the `a_tm` (the argument being passed to the injected lambda) has a much higher probability of being a `Var` rather than a `Lit`, directly targeting an increase in the `used_vars_proportions_average` which currently sits at 0.46.

4. **Asymmetric Budgeting for Function-Type Applications**: When generating a standard `App` (non-redex) where the result type `ty` is a `FunTy`, apply the `0.7` asymmetric budget split to the function side (`f_tm`). This encourages the creation of complex higher-order functions and deeper lambda chains, which provides more opportunities for the successful "must-generate" lambda fallback to trigger, increasing both `tm_sizes_average` and `applied_lambdas_proportions_average`.

5. **Refine Variable Selection with "Shadowing-Aware" Weights**: While the current quadratic bias `(i + 1)**2` is successful, it can be improved by adding a small bonus to variables that match the target type but are *not* the most recently added (e.g., `(i + 1)**2 + (10 if name.startswith("r") else 0)`). This encourages the generator to use variables created by redex injections (`r_` prefix) even if they are slightly further up the stack, maximizing the utility of the specific structural injections that define the current best-performing generation.
