# Performance Optimization Analysis

## Successful Algorithmic Patterns

*   **Cubic Recency Bias for Variable Selection**: The current best program (**Generation 30/33**, score **12.70**) successfully transitioned from quadratic `(i+1)**2` to cubic `(i+1)**3` weighting for variable selection. This change, when paired with high-density redex injection, pushed the `used_vars_proportions_average` to a peak of **0.49**, the highest recorded across all generations.
*   **Forced Variable Arguments in Redexes (90% Rule)**: A critical driver for the 12.70 score is the "Forced Variable Argument" logic. When a redex is injected, the generator selects an existing variable from the context to serve as the argument with a **90% probability**. This creates a synergistic effect where `applied_lambdas` (0.64) and `used_vars` (0.49) are optimized simultaneously.
*   **Budget-Scaled Redex Probability with Asymmetric Splitting**: Top-performing programs (**Generations 30-34**) all utilize a dynamic redex probability formula: `0.55 + (budget / 150.0)`. Combined with a **70/30 asymmetric budget split** (directing 70% of resources to the function body), this ensures that terms remain deep and complex, maintaining an average term size of **~19.43** while keeping a perfect **1.00 validity ratio**.
*   **Context-Aware Type Selection (CATS)**: By sampling `arg_ty` from the existing context (85% probability) rather than generating random types, programs like **Generation 33** ensure that application nodes have a high likelihood of being able to use a local variable, directly supporting the high variable utilization metrics.

## Ineffective Approaches

*   **Exponential Weighting Over-Saturation**: While **Generation 34** used exponential weighting to favor recent variables, it achieved a lower `used_vars` score (0.47) compared to the cubic bias (0.49) of **Generation 33**. This suggests that while recency bias is good, extreme exponential decay may narrow the selection pool too much, slightly reducing the overall variety of variables used.
*   **Static Redex Probabilities**: Earlier iterations (referenced in previous insights like **Generation 19**) that used fixed probabilities (e.g., 55%) for redexes consistently failed to break the 12.60 score barrier. They lacked the structural density required to maximize the `applied_lambdas` metric, which requires aggressive injection early in the recursion (when budget is high).
*   **Uniform Budget Distribution**: Programs that split the budget 50/50 between application branches (seen in early generations) resulted in shallower terms and lower `tm_sizes_average`, which limited the opportunities for both lambda abstraction and variable reuse.

## Implementation Insights

*   **Synergistic Metric Coupling**: The current best program (**Generation 30/33**) treats redexes as "variable delivery vehicles." By forcing the argument of an `App(Lam...)` to be a `Var`, it ensures that every increase in the `applied_lambdas` metric also contributes to the `used_vars` metric. This coupling is the primary reason for the jump to a **12.70** score.
*   **Type-Biased Generation**: Successful programs (**Generation 32**) utilize an **85% bias toward function types** in the `gen_type` function. This increases the "surface area" for applications and lambdas, which are the highest-scoring structural elements.
*   **Collision-Resistant Naming**: To maintain a high `unique_subterms` score (**0.96**), the best programs use a four-part naming convention: `prefix + depth + counter + random_int`. This prevents structural identity between different branches of the term tree, even when the logic (like an identity function) might otherwise be identical.

## Performance Analysis

*   **The 12.70 Performance Peak**: **Generation 30** and **Generation 33** represent the current state-of-the-art with a score of **12.70**. The defining characteristic of these programs is the combination of **Cubic Recency Bias** and **Forced Variable Redexes**.
*   **Variable Usage vs. Validity**: Despite the aggressive cubic bias and forced variable selection, the `good_ratio` has remained a perfect **1.00**. This indicates that the CATS (Context-Aware Type Selection) strategy provides a sufficiently safe "fallback" to ensure type-correctness even when the generator is heavily biased toward specific variables.
*   **Redex Density Correlation**: There is a clear correlation between the `applied_lambdas_proportions_average` and the total score. Programs that achieved **0.64** in this metric (**Generations 30, 32, 33**) consistently outperformed those in the **0.58-0.61** range (**Generations 31, 34**), confirming that redex injection is the most impactful optimization for the current scoring rubric.

The following are actionable recommendations for the next program generations:

1. **Implement "Double-Redex" Injection Chains**: To push the `applied_lambdas_proportions_average` beyond the current 0.64 ceiling, modify the redex logic to occasionally (20% chance) inject a nested redex structure: `(App (Lam x (App (Lam y body) arg2)) arg1)`. This creates a high-density cluster of applications and introduces two variables into the context simultaneously, which synergizes with the cubic recency bias to significantly boost variable utilization.

2. **Introduce Depth-Dependent Constructor Weighting**: Shift the `weights` for constructor selection dynamically based on the remaining budget. By increasing the weight of `App` and `Lam` at high budgets (e.g., `app: 80` when `budget > 50`) and aggressively pivoting to `Var` and `Lit` as the budget depletes, you can create "top-heavy" trees that maximize structural complexity and term size without risking recursion limits or validity.

3. **Implement "Shadowing-Aware" Variable Selection**: While cubic bias is effective, it can be improved by adding a "relevance bonus" to variables created by redexes. Add a weight multiplier (e.g., `1.5x`) to variables in the context that have the `r_` prefix; this ensures that the specific variables injected to drive the `applied_lambdas` metric are also the ones most likely to be selected for the `used_vars` metric, tightening the coupling between these two scores.

4. **Context-Driven Type Matching for Standard Applications**: In the "Standard application" branch (non-redex), instead of generating a random `arg_ty`, prioritize selecting a type that already exists in the `ctx`. This ensures that the argument side of the application (`a_tm`) has a much higher probability of being a `Var` rather than a `Lit` or a new complex term, directly targeting an increase in the `used_vars_proportions_average` which currently sits at 0.49.

5. **Asymmetric Budgeting for Function-Type Results**: When generating an `App` where the expected result type `ty` is a `FunTy`, increase the asymmetric budget split to 80/20 in favor of the function side (`f_tm`). This encourages the creation of complex higher-order functions and deeper lambda chains, providing more opportunities for the "must-generate" lambda fallback to trigger, which increases both `tm_sizes_average` and the density of applied lambdas.
